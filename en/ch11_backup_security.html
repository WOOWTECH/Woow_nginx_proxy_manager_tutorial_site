Chapter 11

Backup, updates and hardening

Run NPM the way you would run any network entry point: confirm the backup really holds the database, the config and the certificates before you update, and keep port 81 on a trusted admin surface, so backups and logs do not become another place sensitive data leaks from.

Define a recoverable operations boundary first

Woow Nginx Proxy Manager is a Home Assistant add-on, not the official NPM Docker Compose deployment as it comes. The add-on config.yaml currently maps addon_config into the container as writable, and publishes only 80, 81 and 443. Woow's patch changes the /data state path that upstream normally uses to /config.

PlaneWhat it holdsOperating rule
Data planeSQLite, the NPM objects, the generated Nginx config, certificates and keysProtect it with HA backups; do not take it apart by hand and then assume it can be restored
Management planePort 81, the administrators and their permissionsRestrict it to a trusted network segment; it must never be exposed to the public internet
Traffic plane80/443 and the public services you have explicitly approvedExpose only the entry points you need; keep the upstream private
Audit planeThe HA add-on log and NPM audit informationKeep the minimum, redact it before you share it, and limit who can read it
Deal with the default credentials now: the Woow README and the CHANGELOG both confirm that the add-on ships with admin@example.com/changeme. You must change the email and set a strong password immediately after your first login. Until that is done, do not create any public entry point, and certainly do not expose port 81.

What an HA backup holds for NPM

The Woow README states that a Home Assistant backup includes all settings, SSL certificates and the database, while config.yaml excludes logs with backup_exclude: "*/logs". Going by the current add-on documentation, the main things to protect are below; what actually ends up in the archive still depends on the backup type you create and on the add-on version at the time.

What it holdsCurrent add-on pathSensitivity / purpose
SQLite database/config/database.sqliteThe core state of your Hosts, users and NPM settings; treat it as sensitive data
Application keys/config/keys.jsonEncryption-related keys; never paste them into a ticket or a public repository
Nginx config/config/nginx/May reveal domains, private IPs, ports and your routing structure
Let's Encrypt data/config/letsencrypt/Holds certificate files and private keys; it must be protected strictly
Custom certificates/config/custom_ssl/May contain private keys; never send it through ordinary messaging
Access Lists/config/access/Holds access control data; do not treat it as publishable config
Logs*/logsExcluded by the add-on's backup rule; the Woow patch already sends some Nginx logs to the add-on output
Do not copy database.sqlite on its own and call the backup done. The database, the keys, the certificates and the generated config all depend on each other. Use the backup/restore flow Home Assistant supports, and confirm the Woow add-on is selected in the backup.

Make a usable backup before updating

  1. Record the current state

    In a private operations record, write down the HA version, the version the Woow add-on shows, the test results for your key Proxy Hosts, and the time of the backup. Do not write down passwords, DNS API tokens, certificate private keys, full domains or unredacted IPs.

  2. Create the backup on the HA backups page

    Go to Settings / System / Backups and create a manual backup, or confirm that "backup before update" is enabled. If you use a partial backup, select the Woow Nginx Proxy Manager add-on explicitly.

  3. Keep the emergency kit

    The official Home Assistant documentation notes that a backup can be encrypted, and that restoring an encrypted backup needs the matching encryption key. Store the Backup emergency kit somewhere safe, away from the HA host, and note which backups it applies to.

  4. Keep a copy on another system

    Do not leave your only backup on the same HA storage device. The official advice is to keep at least one copy on another system, and ideally an off-site copy as well; both need access control.

  5. Confirm it finished, not only that you pressed the button

    Check that the backup job succeeded, that the file exists and its size is plausible, and that the add-on is listed in the selected contents. If your environment allows it, schedule an isolated restore drill.

Turn "downloadable" into "restorable"

A backup you have never rehearsed only proves that a file was produced once; it does not prove that NPM can come back to a working state. Restoring directly on your live HA overwrites whatever you selected, so do it in a maintenance window or on an isolated test device. Do not experiment on production.

  1. Prepare an isolated environment

    Avoid having the restored 80/443 face the outside at the same time as your existing NPM, and avoid pointing test DNS at the live service.

  2. Use the official HA restore flow

    Select the matching backup and the Woow add-on, and supply the encryption key when prompted. Do not unpack it by hand and overwrite an incomplete directory.

  3. Verify the core objects

    Confirm that an administrator can log in, and that the counts of Proxy / Redirection Hosts, Certificates, Access Lists and Streams look right; compare against rewritten inventory data only.

  4. Test the service without exposing it

    Confirm that the add-on starts, that the Nginx config loads, and that a test upstream can be proxied. Shut the isolated instance down once you are finished, so you do not end up with two entry points.

Update on the add-on's release cadence

The Woow config.yaml currently declares version 2.12.4-v2, and addon_info.yaml maps it to upstream NPM v2.12.4. The latest upstream NPM release may be higher, but that does not mean you can apply the Docker update commands directly inside the add-on container.

  1. Read the Woow CHANGELOG and release notes

    Work out whether this is an upstream NPM version upgrade or a fork revision of the same upstream version, and look at the known limitations.

  2. Take a backup and an external test baseline

    Keep your pre-update HTTP/HTTPS, certificate and WebSocket test results, so that if something breaks you can tell whether the update caused it.

  3. Update the add-on from Home Assistant

    Use the add-on update flow HA provides. Do not run docker compose pull from the official Docker documentation inside the container, and do not swap the image.

  4. Read the startup log

    Confirm that the database migration, the NPM backend and Nginx all started. The Woow CHANGELOG already notes that the 0.0.0 the UI/API shows is a known cosmetic problem, so do not judge the update by that number alone.

  5. Verify in order, and be ready to roll back

    Test the admin surface and the internal upstream first, then external 80/443, SSL, redirects and WebSocket. If you hit a serious regression, roll back with a verified HA backup; do not casually downgrade the database file.

Keep port 81 on the admin surface only

The Woow config.yaml maps 81/tcp as the Admin Web Port, and the CHANGELOG says explicitly that 80/81/443 are published on the LAN. That does not make 81 suitable for access from the internet.

  • On the router, forward only the 80/443 your architecture needs; any WAN → 81 rule should be removed.
  • Do not point a Cloudflare Tunnel, a Proxy Host or any other public entry point at http://<HA-private-IP>:81.
  • On the router, the firewall or a VLAN ACL, allow only trusted management devices / the management segment to reach 81 on HA.
  • Guest, IoT and general user segments should not be able to reach 81. For remote administration, prefer a controlled VPN over a public admin page.
  • Changing the external mapped port only cuts down scanning noise; it does not replace a firewall, a strong password and least privilege.
Port 81 serves the admin interface over HTTP. Even once you have changed the credentials, do not let it be exposed directly to the public internet. Treat domains, public and private IPs, passwords, DNS API tokens, certificates and admin logs all as sensitive.

Admin accounts, tokens and certificates

ItemMinimum requirementWhat you must not do
NPM administratorReplace the default email/password immediately; give each person their own account with only the permissions they needShare the default account, or keep the password in a browser screenshot
DNS API tokenGrant only the zones and the DNS edit permission you need, and rotate it regularlyUse a Global API Key, or paste it into a public issue
Certificates and private keysLimit who can read the backups, the files and the admin interfaceSend a private key by email, chat or Git
Domains and IPsKeep operations documents access-restricted, and rewrite every example you publishPublish the domain, the public IP, the private IP and the port mapping together
LogsTake only the lines you need from around the time of the failure, and redact them firstUpload a full add-on log, Authorization, Cookie or DNS credentials

Deleting a user, a certificate or a Host affects the service immediately. If you cannot confirm what something is for, first take stock of its owner, the Hosts that depend on it and when it was last used. Do not delete unknown items in bulk in the name of "cleaning up".

FAQ

Is backing up database.sqlite enough on its own?
No. The state the Woow documentation lists also includes keys, the Nginx config, Let's Encrypt, custom certificates and Access Lists. Use the add-on backup flow HA supports.
The backup is encrypted — do I still need to restrict access?
Yes. Keep the backup and the emergency kit apart, restrict access to both, and hold a copy on another system. The official documentation notes that a download from the HA page may be decrypted on the fly, so the downloaded file needs the same protection.
Can I follow upstream NPM and run docker compose pull directly?
Not on this HA add-on. Woow has its own image, patches, version and HA update flow, so wait for the add-on update Woow publishes and install that.
Does changing port 81 to a different number make it safe?
No. Changing the port only reduces routine scanning. The admin interface must still be closed to the public internet, backed by a trusted management segment, a strong password and least privilege.
