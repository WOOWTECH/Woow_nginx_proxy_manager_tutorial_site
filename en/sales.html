Give every internal service a memorable, safe address

Nginx Proxy Manager (NPM) puts the usual Nginx reverse proxy and certificate settings into a web interface. You do not have to remember a port for every service, and you can manage domains, HTTPS and basic access restrictions in one place.

Proxy HostA friendly reverse proxy
Custom domainsA name instead of an IP and port
HTTPSRequest and renew certificates in one place
Access ListAn extra restriction at the entry point

Why you'd want NPM

Home Assistant, a NAS, a photo library, media or internal tools usually each come with their own IP and port. Exposing them to the public internet one by one is not only hard to remember; it also increases the chance of a configuration slip and widens the attack surface.

NPM lets a request reach one entry point first, then forwards it to the right service by domain name. For example, home.example.com points at Home Assistant and photos.example.com points at the photo library. When a backend address changes, you only update the proxy settings.

In one line: NPM is the front desk for your services; you give a visitor one clear address, and it takes the connection safely to the right service.

How one connection travels

  1. DNS finds the entry point

    At your DNS provider you point the service domain at your home's static IP, at a managed host, or, in a Tunnel setup, at Cloudflare.

  2. TLS sets up HTTPS

    The browser checks the certificate for the domain. When NPM terminates TLS, it uses the certificate you assigned to that Proxy Host.

  3. NPM matches the hostname

    NPM applies the Proxy Host, the Access List and the related settings for that domain, then forwards to the backend service.

  4. The backend still defends itself

    The application remains responsible for accounts, MFA, authorization, patching and data protection; it cannot rely on the proxy entry point alone.

Running it on HAOS

If you already run Home Assistant OS (HAOS), you can evaluate a community-maintained Nginx Proxy Manager add-on. The usual sequence is to back up HAOS first, add a trusted add-on source, set up persistent storage and ports after installing, then log in to NPM and create a Proxy Host.

Verify before you install: a community add-on is not an official component of NPM or of Home Assistant Core. Its source, maintenance status, supported architectures and config keys can change, so go by the documentation for the version you choose.
  • Direct exposure usually needs the router to forward TCP 80/443 to NPM, and confirmation that your ISP is not using CGNAT.
  • If you use it on the local network only, pair it with internal DNS; there is no need to put the services on the public internet.
  • One HA host carrying both the automations and the proxy is convenient to manage, but it becomes a shared point of failure; have a restorable backup before you update.

OptionFits if you care aboutMain cost

Managed / cloud NPMA more stable public entry point, with a provider maintaining the host and the monitoring.There is an ongoing cost; a cloud NPM still needs a secure channel to the backends at home, and you have to settle the data, the keys, the backups and how you would leave.
Cloudflare Tunnel with NPMNot being able or willing to open inbound 80/443, and publishing services over an outbound tunnel instead.Your traffic and TLS design depend on Cloudflare; you have to keep Tunnel rules from bypassing the NPM Access List you expected to apply.

Cloudflare Tunnel can send a public hostname straight to the backend, or send it to NPM. The two topologies differ in where TLS terminates, what the real source IP is, how the Access List behaves and where the logs are. Draw the data flow and run access tests before you adopt one; do not assume that connecting two tools together makes the result safer on its own.

An honest look at the security trade-offs

A reverse proxy is not a security guarantee. It can reduce the direct exposure of backend ports and centralize TLS, but NPM itself also becomes a high-value entry point. The admin interface must not be exposed directly, and it must be updated regularly.
  • Accounts: change the default credentials the moment you first log in and give the administrator a unique, long password; if your NPM version supports stronger authentication, enable it as the official documentation describes.
  • Minimal exposure: keep services that do not need to be public on the LAN or behind a VPN; publish only the domains and ports you need.
  • Two layers of authorization: an Access List is good for filtering at the entry point, but the application itself still needs MFA, role permissions and login auditing.
  • Source IP: with a CDN, a Tunnel or an upstream proxy in front, trust the forwarded headers only once the trusted proxy chain is configured correctly.
  • Backups: back up the configuration, the database and the certificate private keys; encrypt them, restrict who can read them, and run a real restore drill.
  • Availability: a single NPM failure affects every entry point; anything important needs monitoring, a recovery time and an alternative way to connect.

FAQ

Will NPM manage DNS for me?
No. You still create the A, AAAA, CNAME and other records at Cloudflare or another DNS provider; NPM handles the proxying and the certificate settings once the request arrives.
Is HTTPS enough to publish a service safely?
Not on its own. HTTPS protects the transport; it cannot repair a weak password, out-of-date software or wrong authorization. Before you go public you still need updates, MFA, least privilege and backups.
Is Cloudflare Tunnel always safer than opening ports?
It removes the direct inbound ports, but it also adds a third-party dependency and another configuration layer. The security depends on whether the Tunnel routes, Cloudflare Access, NPM and the backend all enforce least privilege consistently.
Is NPM a good fit for enterprise single sign-on?
The NPM Access List is not a full enterprise identity platform. When you need SSO, conditional access or complete auditing, evaluate a dedicated identity proxy separately.

Start with one low-risk service

Take stock of your domains, DNS, backend addresses and what really has to be public, then build your first Proxy Host on a test domain. Only once HTTPS, login, source IP, backup and restore all behave as expected should you move the other services across, one at a time.
