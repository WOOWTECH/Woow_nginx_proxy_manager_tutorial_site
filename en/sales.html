Why you'd want NPM

Home Assistant, a NAS, a photo library, media or internal tools usually each come with their own IP and port. Exposing them to the public internet one by one is hard to remember, increases the chance of a configuration slip and widens the attack surface.

NPM lets a request reach one entry point first, then forwards it to the right service by domain name. For example, home.example.com points at Home Assistant and photos.example.com points at the photo library. When a backend address changes, you update the proxy settings.

In one line: NPM is the front desk for your services; Option A and Option B differ in who operates that front desk, not in the need to secure every backend.

How one connection travels

  1. DNS finds the entry point

    For Option A, you design and operate the entry path. For Option B, the final entry path and division of responsibility remain an owner-approved service-scope decision.

  2. TLS sets up HTTPS

    The browser checks the certificate for the domain. When NPM terminates TLS, it uses the certificate assigned to that Proxy Host.

  3. NPM matches the hostname

    NPM applies the Proxy Host, the Access List and related settings for that domain, then forwards to the backend service.

  4. The backend still defends itself

    The application remains responsible for accounts, MFA, authorization, patching and data protection; neither option replaces those controls.

Running it on HAOS

Option A can use a community-maintained Nginx Proxy Manager add-on on Home Assistant OS (HAOS). Back up HAOS first, review the add-on source, set up persistent storage and ports after installing, then log in to NPM and create a Proxy Host.

Verify before you install: a community add-on is not an official component of NPM or Home Assistant Core. Its source, maintenance status, supported architectures and config keys can change, so follow the documentation for the version you choose.
  • Direct exposure usually needs the router to forward TCP 80/443 to NPM, and confirmation that your ISP is not using CGNAT.
  • If you use it on the local network only, pair it with internal DNS; there is no need to put the services on the public internet.
  • Option A makes you responsible for the shared point of failure, backups and updates; Option B responsibilities must be stated in the owner-approved service scope.

An honest look at the security trade-offs

A reverse proxy is not a security guarantee. It can reduce direct exposure of backend ports and centralize TLS, but NPM itself becomes a high-value entry point. The admin interface must not be exposed directly, and regular updates are required under either option.
  • Accounts: Option A requires you to change the default credentials immediately; Option B must identify who controls administrator access in the approved service scope.
  • Minimal exposure: keep services that do not need to be public on the LAN or behind a VPN; publish only the required domains and ports.
  • Two layers of authorization: an Access List can filter at the entry point, but the application itself still needs MFA, role permissions and login auditing.
  • Source IP: with a CDN, Tunnel or upstream proxy in front, trust forwarded headers only after the trusted proxy chain is configured correctly.
  • Backups: the configuration, database and certificate private keys need encrypted backups, restricted access and a real restore drill; Option B ownership is an open scope item.
  • Availability: a single NPM failure affects every entry point; monitoring, recovery objectives and an alternative connection method must be defined rather than assumed.
