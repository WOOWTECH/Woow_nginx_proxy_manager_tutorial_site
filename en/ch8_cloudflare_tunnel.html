Chapter 8

Cloudflare Tunnel with NPM

Let cloudflared reach out to Cloudflare, terminate external HTTPS at the Cloudflare edge, and leave NPM on the LAN to forward by domain, with nothing opened on the router for 80, 443 or 81.

No need to put your home entry point on the public internet

With Cloudflare Tunnel, a cloudflared inside your network opens an outbound-only connection, and Cloudflare's official documentation states that no publicly routable IP is required. That suits a home network with no fixed public IP, one behind CGNAT, or one where you would rather not maintain inbound forwarding on the router.

The recommended split: Cloudflare accepts public HTTPS, the Tunnel hands the request to NPM's HTTP entry point on the LAN, and NPM then forwards by Host name to Home Assistant, a NAS or another internal service.
Admin security baseline: you must change the default admin@example.com / changeme immediately. A Cloudflare Tunnel may only publish your application services, never NPM port 81; port 81 must never be port-forwarded on the router either.

Your pre-build checklist

  1. Confirm Cloudflare manages the domain

    You need to be able to create a Tunnel and a public hostname in your own Cloudflare account. Treat the domain, the account ID and the zone ID as sensitive data.

  2. Prepare a connector that can run long term

    Run cloudflared on a trusted device that can reach NPM over the network. This chapter does not tie you to any particular third-party add-on; use an installation method Cloudflare officially supports, or a package you have reviewed yourself.

  3. Confirm the internal path

    The connector must be able to reach NPM port 80, and NPM must be able to reach the upstream service. Both hops only need to work inside the LAN, which is not the same as opening them to every LAN device.

  4. Take stock of the port forwards you already have

    If you already use public 80/443, record what depends on it and how to roll back. Only once every hostname has been migrated and tested should you disable the old rules, following your change process; do not simply delete them while you are unsure of the impact.

Make NPM route by domain first

  1. Add a Proxy Host

    In NPM, go to Hosts → Proxy Hosts → Add Proxy Host and put the full hostname you will publish on the Tunnel later into Domain Names. Keep your real domain out of tutorial screenshots and public tickets.

  2. Set the internal upstream

    Enter the service's private address and port in Forward Hostname / IP and Forward Port, and set the Scheme to whichever the upstream actually offers, HTTP or HTTPS. A private IP is still sensitive topology data.

  3. Do not request a public certificate yet

    The recommended Tunnel Service URL reaches NPM on HTTP port 80 and Cloudflare handles external TLS, so at this point NPM does not need a Let's Encrypt certificate for external browsers.

  4. Do not turn on Force SSL

    When Cloudflare connects to NPM over HTTP, Force SSL can send the same external HTTPS URL around a redirect again and again. Leave it off for now; external HTTP to HTTPS is handled by a Cloudflare edge setting.

Create and start the connector

  1. Create a named Tunnel in Cloudflare

    Create the Tunnel through the Zero Trust / Networks / Tunnels flow in the Cloudflare Dashboard; the interface names may have changed, so go by the current official documentation.

  2. Choose the connector environment

    Use the official installation method Cloudflare shows for your platform. The tunnel token on that screen is the secret that can start a connector, so never paste it into a chat, a command history, a screenshot or a repository.

  3. Supply the token safely

    Store the token in that platform's secret or protected settings, readable only by the connector process. If it has ever leaked, rotate or revoke it in Cloudflare immediately rather than just deleting the message.

  4. Confirm the status is Healthy

    The connector needs outbound DNS, and it connects to port 7844 as described in Cloudflare's official firewall documentation (UDP for QUIC, TCP for HTTP/2). No public inbound rule is needed.

Point the public hostname at NPM

  1. Add a Published application

    Add a public hostname on that Tunnel. The Subdomain and Domain together must be exactly the same as the Domain Names on the NPM Proxy Host.

  2. Set Service Type to HTTP

    In URL, enter the address at which NPM is reachable on the LAN together with port 80, for example http://<npm-private-address>:80. That is only a format example; do not commit a real private IP to a public document.

  3. Save it and confirm DNS

    Cloudflare routes the hostname to the Tunnel; the official documentation explains that this is really a CNAME pointing at <UUID>.cfargotunnel.com. One Tunnel can serve several hostnames.

  4. Create one NPM entry per hostname

    When you add a service, add the Published application and the matching NPM Proxy Host together. Do not send every unmatched hostname to the admin interface.

The routing key: Cloudflare receives the request on the public hostname, and NPM picks the Proxy Host by that same Host; when the two strings differ, you usually land on the default page or a 404.

Separate external TLS from the internal origin hop

HopRecommended settingWhy, and the limits
Browser → CloudflareHTTPS, with HTTP redirected to HTTPS at the Cloudflare edgeThe browser validates the edge certificate Cloudflare presents for that hostname
Cloudflare Tunnel → NPMHTTP on port 80, inside an isolated LANSimple to set up and it needs no public certificate on NPM, but this hop is unencrypted and must stay on a trusted network
NPM → internal serviceHTTP or HTTPS, whichever the service supportsNPM's Scheme must match the protocol the upstream actually speaks
If the internal hop must be encrypted too: you can point the Tunnel Service URL at NPM over HTTPS, but you then have to give NPM a certificate that is correct, name-matching and verifiable by the connector. Do not paper over a certificate error by disabling TLS verification.
Force SSL belongs in exactly one place: with an HTTP Service URL on the origin hop, leave Force SSL off in NPM; the external HTTP to HTTPS redirect is handled at Cloudflare. Do not turn both on because instinct says to.

A Tunnel is not full authentication

  • Never publish port 81: a Tunnel's public hostname points only at the proxy entry on NPM port 80/443, never at the admin interface.
  • Minimal exposure for every hostname: publish only the services you genuinely need to use from the public internet. A database, SSH or a NAS admin page should not go public alongside them just because a Tunnel is easy to set up.
  • Redact sensitive values at every step: domains, public and private IPs, the tunnel token, DNS API tokens, passwords, certificates and full logs must all stay private.
  • Add Cloudflare Access when you need user identity: a Tunnel only builds the transport path; if a service should not be used anonymously, you still need suitable controls in the application, in Cloudflare Access, or in the Access List from Chapter 9.
  • Limit the network between the connector and NPM: allow only the connector-to-NPM and NPM-to-upstream traffic you need, and do not treat the whole LAN as trusted.

Verify hop by hop, inside out

  1. Test NPM to the upstream

    First confirm from the LAN that the upstream service is reachable and that the Scheme and port are right. Do not open more public ports just because you got a 502.

  2. Test Host routing

    From a trusted LAN, request NPM with that hostname and confirm it lands on the right Proxy Host rather than on the default site.

  3. Confirm the connector is healthy

    In Cloudflare, check whether the Tunnel has a connector currently connected. Record only the status and the time; do not publish the UUID, the token or a full diagnostic log.

  4. Test HTTPS from outside

    Open the public hostname over mobile data and confirm HTTPS, login, WebSocket and any function you need; then test whether HTTP is redirected to HTTPS at the Cloudflare edge.

  5. Confirm the router has no unnecessary inbound rules

    Once you have verified everything, follow your change process to check that public 80, 443 and 81 are not forwarded to NPM. If an old service still depends on a rule, migrate it first and keep a rollback plan.

Cloudflare Tunnel FAQ

Does this architecture need the router to forward 80 or 443?
No. cloudflared opens an outbound-only connection to Cloudflare; the recommended topology uses no public inbound 80 or 443, and never exposes 81.
Can I use it with no public IP, or behind CGNAT?
Yes. Cloudflare officially positions a Tunnel as a connection method that needs no publicly routable IP, but the connector still has to be able to connect outbound and resolve DNS.
Why is Force SSL left off in NPM?
This chapter has the Tunnel connect to NPM over HTTP. If NPM forces a redirect back to HTTPS, Cloudflare still connects back to the origin over HTTP the next time, which can cause a redirect loop; the external redirect belongs at the Cloudflare edge.
Can one Tunnel publish several services?
Yes. Cloudflare's official documentation explains that several DNS records can point at the same Tunnel; each public hostname should still get an explicit matching Proxy Host in NPM.
Does having a Tunnel remove the need for a service login?
No. A Tunnel solves the connection path; it does not automatically create user authentication for each application. Keep the application's login, or add Cloudflare Access or an NPM Access List as you need them.
