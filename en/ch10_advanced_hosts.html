Chapter 10

Redirects, Streams and WebSocket

Work out first whether the traffic is HTTP, WebSocket or plain TCP/UDP, then handle it with the right NPM object. This chapter also covers the port limits of the Woow Home Assistant add-on, and when not to add custom Nginx directives.

Pick the right NPM object first

Proxy Host, Redirection Host and Stream all look like "forwarding", but they work at different layers. Pick the wrong object and the usual results are a redirect loop, a 502, or a service you clearly created but cannot reach at all.

What you wantObject to useKey test
Proxy a website or an API by domainProxy HostUnderstands HTTP/HTTPS; you can apply a certificate, an Access List and path rules
Redirect an old address to a new oneRedirection HostReturns 301 or 302, and the browser goes to the target address
Send different paths to different HTTP servicesCustom Locations on a Proxy HostFor example, /api and / on the same domain go to different upstreams
Forward TCP/UDP without understanding the contentStreamForwards by incoming port to a set host and port; it does not route by domain or URL path
Do not expose the admin interface: port 81 is the NPM Admin Web Port, not an ordinary service entry point. It should only be reachable from a trusted management network segment, and must never be exposed on your router or through Cloudflare. If you are still on the default admin@example.com / changeme, change the email and the password immediately before you do anything in this chapter.

Understanding 301, 302 and path preservation

A Redirection Host makes the client receive a redirect response, rather than having NPM fetch the target content in the background. The Woow add-on documentation explicitly lists support for 301 and 302; the NPM 2.12.4 interface the add-on currently uses also offers fields such as Forward Scheme, Forward Domain, HTTP Code and Preserve Path.

  • 301 permanent redirect: for a domain move you are sure you will not undo. Browsers, search engines and intermediate caches may remember the result, so a mistake made while testing is hard to take back right away.
  • 302 temporary redirect: for maintenance, a campaign page, or validating a rule first. Once you have confirmed it is correct, decide whether to switch it to 301.
  • Preserve Path: when it is on, the path after the old address is carried over to the new domain; before you turn it off, confirm whether you really only want to land on the home page.
Go live with 302 first. Verify the hostname, the path, the query string and HTTPS from a private window and from an external network, then decide whether to switch to 301.

Create a safe redirect

  1. Take stock of the source and the target

    Using rewritten test data, write down the source domain, the target domain, whether the path is preserved, and whether you plan to use 302 or 301. Treat domain and certificate details as sensitive operations data; do not paste them straight into a public forum.

  2. Add a Redirection Host

    In NPM, add an entry under Hosts / Redirection Hosts and fill in the source Domain Names, Forward Scheme and Forward Domain Name. Choose 302 while you are testing, and set Preserve Path to suit what you need.

  3. Handle HTTPS on the source domain

    If people will open the old domain over HTTPS, the source side still needs a valid certificate: the browser only receives the redirect response once TLS has completed. Pick the right certificate on the SSL tab, and do not write a private key or a DNS API token into your notes.

  4. Verify from outside

    Confirm that the response code and the Location target are what you expect, and test a deep path as well. Do not judge by the final page alone, or the browser will follow the redirect automatically and hide the errors in between.

Streams forward TCP/UDP

The official NPM documentation defines a Stream as forwarding TCP/UDP traffic straight to another machine on the network, which suits protocols an HTTP Proxy Host cannot handle. At a minimum the settings cover Incoming Port, Forwarding Host, Forwarding Port, and the choice of TCP and UDP.

CheckWhySafe practice
ProtocolTCP and UDP are not interchangeableEnable only the protocol the service actually needs
Incoming PortA Stream accepts by port only; it does not route by domainAvoid clashing with 80, 81, 443 or another service
Forwarding Host / PortNPM must be able to reach the upstream from the add-on networkUse a fixed private address and restrict the upstream firewall
Public exposureA non-HTTP service usually has no NPM Access List protecting itUse a VPN first; if it really must be public, narrow it down with source IP rules and the service's own authentication
What the Woow add-on actually allows: right now config.yaml declares only 80/tcp, 81/tcp and 443/tcp, with no option for an arbitrary Stream port. Creating a Stream in the NPM UI does not mean the HA host has published that incoming port. Do not take over port 81, and never forward the admin port to the public internet to make a Stream work; check the settings of a newer add-on release first, or move to a controlled deployment that can map the ports you need explicitly.

Let WebSocket upgrade correctly

A WebSocket starts as an HTTP request and then switches to a long-lived connection through the Upgrade mechanism. A Proxy Host in NPM 2.12.4 has a Websockets Support option; the matching official template sets Upgrade, Connection and HTTP/1.1. You normally do not need to write those directives out again by hand.

  1. Test the upstream directly first

    From the same LAN, confirm that the application itself can establish a WebSocket. If it drops on a direct connection, fix the application first rather than guessing from NPM.

  2. Edit the right Proxy Host

    Turn on Websockets Support under Details, save, and test again. If a Custom Location points at a different upstream, check that location's WebSocket settings and path as well.

  3. Confirm with the browser developer tools

    Look at the WS entries under Network, the handshake status and the close code. Before you record anything, redact domains, Cookie, Authorization, query parameters and private and public IPs.

  4. Rule out the layers in between, one at a time

    If a direct connection to NPM works and it only fails through Cloudflare, then look at Cloudflare or the Tunnel. Do not change NPM, DNS and the application at the same time.

Split by path with Custom Locations

Custom Locations are HTTP path rules inside a single Proxy Host. The official NPM 2.12.4 template gives each location its own scheme, forward host, forward port and optional advanced config, and applies the access control, SSL enforcement and WebSocket fragments.

  1. Map out a path table

    List which upstream /, /api and /socket should each go to. Test the longer, more specific paths on their own.

  2. Add one location

    Under Custom Locations on the Proxy Host, add the path and the Forward Scheme / Hostname / Port. Keep the settings to a minimum at first, and do not start by pasting in an Nginx snippet you found online.

  3. Check the application's base path

    Some applications can only be deployed at the root path; others need an external URL or a base path set. If the page opens but its assets return 404, check the URLs the application generates first.

  4. Verify path by path

    Test the home page, the API, static assets, the login callback and WebSocket. Change one location at a time, and keep a record of the settings you can roll back to.

The path rules on a Custom Location and the Advanced config can override the behavior you expect. Back up before you change anything, and do not add an include of unknown origin, a rule that bypasses authentication, or a directive that writes certificates, tokens or passwords into responses and logs.

Hold the line before you customize Nginx

NPM does officially provide an advanced Nginx config, but that does not mean every snippet on the internet is fit to paste in. The Woow add-on also moves the upstream project's data path from /data to /config and sends several Nginx logs to the add-on output, so take particular care when you follow a generic Docker tutorial.

  • Use the built-in UI options first: WebSocket, SSL, Access List, Custom Locations.
  • Add one directive at a time, one you can explain; back up before you save, and test your existing paths immediately after.
  • Do not hand-edit the auto-generated files in /config/nginx/proxy_host/; the UI may overwrite them when it rebuilds the config.
  • Do not put passwords, DNS API tokens, private keys, a full list of internal and external addresses, or unredacted logs into the Advanced field.
  • If a setting makes an Nginx reload fail, remove the last thing you customized first; do not delete the database or the certificate directory.

FAQ

Can a Redirection Host act as a reverse proxy?
No — you cannot treat them as the same thing. A redirect tells the browser to go to another URL; with a reverse proxy, NPM connects to the upstream on the client's behalf and the browser can stay on the original domain.
Can one Stream send different domains to different servers?
A normal Stream forwards TCP/UDP by incoming port; it does not route on the HTTP Host or the URL path. If what you want is routing by website domain, use a Proxy Host.
Does turning on Websockets Support fix every real-time connection automatically?
No. It adds the upgrade settings the NPM proxy needs, but the upstream path, the application's own settings, timeouts and other layers in between can still drop the connection.
Can I copy an Advanced config from the community as-is?
Not recommended. Understand every directive first, confirm it applies to NPM 2.12.4 and to Woow's /config path, and test them one at a time once you have a backup you can restore from.
