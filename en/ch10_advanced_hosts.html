Chapter 10

重導向、Streams 與 WebSocket

先辨認流量是 HTTP、WebSocket，還是一般 TCP／UDP，再用正確的 NPM 物件處理。這一章也會說明 Woow Home Assistant add-on 的連接埠限制，以及何時不該加入自訂 Nginx 指令。

先選對 NPM 物件

Proxy Host、Redirection Host 與 Stream 看起來都像「轉送」，實際處理的層級不同。選錯物件時，最常見的結果是無限重導、502，或服務明明建立了卻完全連不到。

需求使用物件判斷重點
以網域代理網站或 APIProxy Host理解 HTTP／HTTPS，可套用憑證、Access List 與路徑規則
把舊網址導到新網址Redirection Host回傳 301 或 302，瀏覽器會改向目標網址
依路徑送到不同 HTTP 服務Proxy Host 的 Custom Locations例如同一網域的 /api 與 / 使用不同 upstream
轉送不理解內容的 TCP／UDPStream依 incoming port 轉到指定主機與埠，不依網域或 URL 路徑分流
不要公開管理介面：port 81 是 NPM Admin Web Port，不是一般服務入口。它只應從可信任的管理網段存取，絕對不要在路由器或 Cloudflare 公開它。若仍使用預設 admin@example.com／changeme，先立即更換 email 與密碼，再做本章操作。

理解 301、302 與路徑保留

Redirection Host 會讓用戶端收到重新導向回應，而不是由 NPM 在背景取回目標內容。Woow add-on 文件明列支援 301 與 302；目前 add-on 使用的 NPM 2.12.4 介面也提供 Forward Scheme、Forward Domain、HTTP Code 與 Preserve Path 等欄位。

  • 301 永久重導：適合已確定不會回復的網域搬遷。瀏覽器、搜尋引擎或中介快取可能記住結果，測試錯誤時較難立即撤回。
  • 302 暫時重導：適合維護、活動頁或先驗證規則。確認無誤後再評估是否改成 301。
  • Preserve Path：啟用時，舊網址後面的路徑會帶到新網域；停用前先確認你是否只想導到首頁。
初次上線先用 302，在無痕視窗與外部網路驗證主機名稱、路徑、查詢字串及 HTTPS，再決定是否改為 301。

建立一個安全的重導向

  1. 先盤點來源與目標

    以改寫過的測試資料記下來源網域、目標網域、是否保留路徑及預計使用 302 或 301。網域與憑證資訊都視為敏感維運資料，不要直接貼到公開討論區。

  2. 新增 Redirection Host

    在 NPM 的 Hosts／Redirection Hosts 新增項目，填入來源 Domain Names、Forward Scheme 與 Forward Domain Name。測試階段選 302，依需求決定 Preserve Path。

  3. 處理來源網域的 HTTPS

    若用戶會以 HTTPS 開啟舊網域，來源端仍須有有效憑證，TLS 完成後瀏覽器才收得到重導回應。在 SSL 分頁選正確憑證；不要把私鑰或 DNS API token 寫入筆記。

  4. 從外部驗證

    確認回應碼與 Location 目標符合預期，並測試深層路徑。不要只看最後畫面，否則瀏覽器自動跟隨重導後會藏起中間錯誤。

Streams 是 TCP／UDP 轉送

NPM 官方說明將 Stream 定義為把 TCP／UDP 流量直接轉到網路中的另一台主機，適合無法用 HTTP Proxy Host 處理的協定。設定至少包含 Incoming Port、Forwarding Host、Forwarding Port，以及 TCP、UDP 的選擇。

檢查原因安全做法
協定TCP 與 UDP 並不互通只啟用服務實際需要的協定
Incoming PortStream 只依連接埠接收，不依網域分流避免與 80、81、443 或其他服務衝突
Forwarding Host／PortNPM 必須能從 add-on 網路連到 upstream使用固定私有位址並限制 upstream 防火牆
外部暴露非 HTTP 服務通常沒有 NPM Access List 保護先用 VPN；確需公開時，以來源 IP 與服務自身驗證限縮
Woow add-on 的實際限制：目前 config.yaml 只宣告 80/tcp、81/tcp、443/tcp，沒有任意 Stream port 的選項。只在 NPM UI 建立 Stream，不代表 HA 主機已發布該 incoming port。不要占用 81，也不要為了讓 Stream 可用而把管理埠轉送到網際網路；請先核對新版 add-on 設定，或改採能明確映射所需埠的受控部署。

讓 WebSocket 正確升級

WebSocket 先從 HTTP 請求開始，再透過 Upgrade 機制切換成長連線。NPM 2.12.4 的 Proxy Host 有 Websockets Support 選項；對應官方範本會設定 Upgrade、Connection 與 HTTP/1.1。通常不必手寫重複指令。

  1. 先直接測 upstream

    從同一內網確認應用程式本身能建立 WebSocket。若直連就斷線，先修應用程式，不要從 NPM 猜測。

  2. 編輯正確的 Proxy Host

    在 Details 啟用 Websockets Support，保存後重新測試。若 Custom Location 指向另一個 upstream，也要確認該位置的 WebSocket 設定與路徑。

  3. 用瀏覽器開發者工具確認

    查看 Network 的 WS 項目、握手狀態與關閉碼。記錄前先遮罩網域、Cookie、Authorization、查詢參數與私有／公開 IP。

  4. 逐一排除中介層

    若 NPM 直連正常、經 Cloudflare 才失敗，再查 Cloudflare 或 Tunnel；不要同時修改 NPM、DNS 與應用程式。

用 Custom Locations 做路徑分流

Custom Locations 是同一 Proxy Host 內的 HTTP 路徑規則。NPM 2.12.4 的官方範本會為每個 location 產生自己的 scheme、forward host、forward port 與可選的 advanced config，並套用存取控制、SSL 強制與 WebSocket 相關片段。

  1. 畫出路徑表

    先列出 /、/api、/socket 各自要到哪個 upstream。較長、較明確的路徑要單獨測試。

  2. 新增一個位置

    在 Proxy Host 的 Custom Locations 加入路徑與 Forward Scheme／Hostname／Port。先保持最少設定，不要一開始就貼入網路上的 Nginx 片段。

  3. 確認應用程式的 base path

    有些應用只能部署在根路徑，有些需要設定 external URL 或 base path。若頁面開得出來但資源 404，優先檢查應用程式產生的 URL。

  4. 逐路徑驗證

    測試首頁、API、靜態資源、登入回呼與 WebSocket。每次只調整一個位置，保留可回復的設定紀錄。

Custom Location 的路徑規則與 Advanced 設定可能蓋過預期行為。改動前先備份；不要加入來源不明的 include、繞過驗證的規則，或會把憑證、token、密碼寫入回應與 log 的指令。

自訂 Nginx 前先守住邊界

NPM 官方確實提供進階 Nginx 設定，但這不代表任何網路片段都適合直接貼上。Woow add-on 又把上游的資料路徑由 /data 改到 /config，並把多種 Nginx log 導向 add-on 輸出；套用一般 Docker 教學時尤其要小心。

  • 先用 UI 原生選項：WebSocket、SSL、Access List、Custom Locations。
  • 一次只加入一個可解釋的 directive，保存前備份，保存後立即測試既有路徑。
  • 不要手改 /config/nginx/proxy_host/ 的自動產生檔案；UI 重建設定時可能覆寫。
  • 不要在 Advanced 欄位放密碼、DNS API token、私鑰、完整內外網位址清單或未遮罩 log。
  • 若設定讓 Nginx reload 失敗，先移除最後一筆自訂內容，不要刪除資料庫或憑證目錄。

常見故障與具體修正

問題先看哪裡具體處理
重導後一直循環來源與目標 scheme／網域，以及 Force SSL暫用 302，確認目標沒有再導回來源；每次只停用一條規則測試
301 改了仍去舊網址瀏覽器與 CDN 快取用無痕視窗、不同用戶端或不自動跟隨的 HTTP 檢查；不要持續改 DNS
Stream 已建立但外部連不到HA add-on 是否真的發布 incoming port核對 config.yaml 與 HA Network；目前 Woow 版本只有 80、81、443，不要拿 81 代用
WebSocket 連上後立刻斷線upstream 直連、WS 路徑與 Websockets Support先直連 upstream，再啟用選項；若只在 Cloudflare 後失敗才查該層
Custom Location 顯示 404應用程式 base path 與實際請求路徑確認應用是否支援子路徑，並檢查靜態資源與登入回呼 URL

常見問題

Redirection Host 能當反向代理嗎？
不能視為同一件事。重導向會叫瀏覽器前往另一個 URL；反向代理則由 NPM 代表用戶端連到 upstream，瀏覽器可維持原網域。
一個 Stream 可以依網域送到不同伺服器嗎？
一般 Stream 是依 incoming port 轉送 TCP／UDP，不使用 HTTP Host 或 URL 路徑分流。若需求是網站網域分流，使用 Proxy Host。
啟用 Websockets Support 會自動修好所有即時連線嗎？
不會。它補上 NPM 代理所需的升級設定，但 upstream 路徑、應用程式設定、逾時與其他中介層仍可能造成斷線。
可以直接複製社群提供的 Advanced 設定嗎？
不建議。先理解每一條 directive、確認適用 NPM 2.12.4 與 Woow 的 /config 路徑，並在可回復備份後逐條測試。
