Chapter 1

Getting to know Nginx Proxy Manager

Build a mental model of the reverse proxy first, then choose the deployment and exposure option that fits you. This chapter is in no hurry to open a port; it maps out the traffic path and the security boundaries first.

Why you need NPM

Your home may run Home Assistant, a NAS or other web services, each on its own LAN address and port. Nginx Proxy Manager (NPM) sits in front of them and forwards HTTP or HTTPS traffic to the right internal service, based on the domain name in the request.

It puts the usual Nginx reverse proxy and certificate work into a web admin interface. The upstream project lists domain forwarding, redirects, Streams, SSL certificates, Access Lists, user permissions and an audit log; DNS, the router and the security of the backend services are still yours to manage.

Remember: NPM is an entry point and a forwarding layer, not a switch that makes internal services secure by itself. Before you expose anything, update the backend, turn on its login protection, and enable only the features you need.

How a request flows

  1. Name resolution

    The browser queries DNS for the service domain first. With direct exposure the answer usually points at your home's public IP; with a Tunnel the traffic reaches the Tunnel provider first. The domain and the public IP are both sensitive; redact them before you share a screen.

  2. Reaching the entry point

    With direct exposure the router usually forwards external TCP 80/443 to NPM; in a Tunnel setup the existing tunnel carries the request to the internal entry point. TCP 81, the admin interface, is not on this public service path.

  3. Matching a Proxy Host

    NPM picks the rule by the HTTP Host name; for HTTPS, NPM can terminate TLS and then connect to the backend's private address and port as configured.

  4. The backend responds

    The backend's response returns to NPM, and NPM sends it back to the browser. NPM being able to reach the backend does not mean the backend should be exposed to the internet directly.

Map your deployment path first

  1. List the entry point

    Decide between direct exposure and a Tunnel. Do not change the router yet; record the data flow on paper only.

  2. List the NPM host

    Confirm the Home Assistant installation type and the CPU architecture, and confirm that the host is expected to use TCP 80, 81 and 443.

  3. List one test backend

    Pick a service that already has login protection and is reachable from NPM's network segment. The private IPs and service ports in your notes count as sensitive data too.

  4. Draw the admin boundary

    State plainly that TCP 81 is for a trusted LAN or a controlled management channel only, that it never gets a WAN port forward, and that no public DNS record points at it.

Security baseline

  • Your first login uses admin@example.com / changeme; these are published defaults, so you must change the email and the password immediately after you log in.
  • TCP 81 is the admin surface and must never be exposed to the public internet. Do not create a WAN forward for 81 on the router, and do not publish it as an ordinary Proxy Host.
  • Treat domains, public and private IPs, passwords, DNS API tokens, certificate private keys and full logs as sensitive data; rewrite or redact them in every example, screenshot and help request.
  • Expose 80/443 only when you are certain you need to. With a Tunnel, narrow the firewall entry points to match that design instead of also keeping a direct exposure you do not need.
Never paste a real password or token into your notes. Passwords belong only in a password manager vault you trust; a DNS token should carry the least privilege the provider offers.

Concept troubleshooting

Problem 1: assuming that creating a Proxy Host creates DNS

NPM does not register a domain for you or set up public DNS on its own. Confirm the DNS and the entry-point plan first, then create the matching host.

Problem 2: treating TCP 81 as a public site entry point

81 is the admin interface. Remove any WAN forward or public proxy rule for it, and manage it only from a trusted LAN or a controlled channel.

Problem 3: 80 or 443 is already in use by another add-on

Two services cannot listen on the same port for the same host address and protocol. Take stock of the conflict first; do not disable an existing service before you understand the impact.

Problem 4: believing HTTPS means the backend is already secure

HTTPS protects the transport; it does not fix a weak password, outdated software or wrong permissions. Go back to the backend and work through the login, the updates and least privilege one by one.

Problem 5: running a Tunnel and an unnecessary WAN forward at the same time

That leaves a second entry point. Check the firewall and the router item by item against the design you chose, and keep no public path you do not use.

FAQ

Will NPM replace Home Assistant?
No. NPM is the reverse proxy entry point; Home Assistant is still a separate backend service.
Can I install it before I have a domain?
You can install it and harden the account on a trusted LAN first, but proxying a real domain and issuing a public certificate still need the matching name resolution and challenge conditions.
If I use a Tunnel, do I still need NPM?
It depends on your routing needs. The Woow documentation shows a Tunnel that delivers traffic to NPM, with NPM doing the internal routing; if you have no multi-host routing to do, weigh up whether the extra layer is worth it first.
Can I put the admin interface on a public domain?
This guide does not recommend it and does not show how. TCP 81 belongs on a trusted LAN or a controlled management channel, and must never be exposed directly.
