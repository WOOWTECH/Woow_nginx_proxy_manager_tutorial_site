Chapter 1

認識 Nginx Proxy Manager

先建立反向代理的心智模型，再選擇適合你的部署與公開方式。這一章不急著開放任何連接埠，而是先畫清楚流量路徑與安全邊界。

為什麼需要 NPM

家中可能有 Home Assistant、NAS 或其他 Web 服務，各自使用不同的區網位址與連接埠。Nginx Proxy Manager（NPM）站在這些服務前方，依請求的網域名稱，把 HTTP 或 HTTPS 流量轉送到正確的內部服務。

它把常見的 Nginx 反向代理與憑證操作放進 Web 管理介面。上游專案列出的能力包括轉送網域、重導向、Streams、SSL 憑證、Access Lists、使用者權限與稽核記錄；你仍須自行管理 DNS、路由器及後端服務的安全。

先記住：NPM 是入口與轉送層，不是把內部服務自動變安全的開關。公開前仍要更新後端、啟用其登入保護，並只開放必要功能。

請求如何流動

  1. 名稱解析

    瀏覽器先向 DNS 查詢服務網域。採直接公開時，結果通常指向你家的公開 IP；採 Tunnel 時，流量先到 Tunnel 服務商。網域與公開 IP 都是敏感資訊，分享畫面前要遮罩。

  2. 抵達入口

    直接公開通常由路由器把外部 TCP 80／443 轉送到 NPM；Tunnel 架構則由既有的通道把請求送到內部入口。管理介面的 TCP 81 不在這條公開服務路徑上。

  3. 比對 Proxy Host

    NPM 依 HTTP Host 名稱選擇規則；HTTPS 可由 NPM 終止 TLS，再按設定連到後端的私有位址與連接埠。

  4. 後端回應

    後端回應先回到 NPM，再送回瀏覽器。NPM 能到達後端，不代表後端應直接暴露在網際網路。

功能與責任邊界

工作NPM 的角色仍由你負責
網域與 DNS接收已抵達入口的網域請求持有網域，建立及維護 DNS 記錄
HTTPS管理 Let's Encrypt 或自訂憑證，並可終止 TLS選擇驗證方式、保護 DNS API Token、檢查續期
轉送把符合規則的流量送往後端確認後端位址、連接埠、驗證與更新
網路邊界提供 HTTP／HTTPS 入口路由器、防火牆、Tunnel 與來源限制
管理介面在 TCP 81 提供 Web UI只允許可信任區網或受控管理通道存取
NPM 不是 DNS 伺服器、網域註冊商、VPN 或完整 WAF。不要因為已啟用 HTTPS，就省略後端登入、更新或最小權限。

部署方式比較

方式適合情境主要取捨
Woow HAOS add-on你使用 Home Assistant OS 或 Supervised，主機是 amd64／aarch64由 Supervisor 管理生命週期；80、81、443 不可與同主機其他服務衝突
官方 Docker 部署你有獨立 Docker 主機並想依官方 Compose 文件管理主機、儲存、更新與備份都要自行管理；本教學後續以 add-on 為主
直接公開 80／443你能控制路由器、防火牆與公開 DNS公開面較大；官方指南的家用網路流程是轉送 80／443到 NPM
Cloudflare Tunnel 搭配 NPM你不想或不能在路由器轉送連接埠不需路由器轉送，但增加第三方依賴；仍要限制 NPM 管理介面

Woow add-on 的設定檔目前宣告 amd64 與 aarch64，並將 TCP 80、81、443 對應到相同主機連接埠。若你的平台或需求不符，不要硬套本教學的安裝步驟。

先畫部署路徑

  1. 列出入口

    決定使用直接公開或 Tunnel。先不要變更路由器；只在紙上記錄資料流。

  2. 列出 NPM 主機

    確認 Home Assistant 安裝類型與 CPU 架構，並確認主機預計使用 TCP 80、81、443。

  3. 列出一個測試後端

    選擇已有登入保護、可從 NPM 網段到達的服務。筆記中的私有 IP 與服務連接埠同樣要視為敏感資料。

  4. 劃出管理邊界

    明確標示 TCP 81 只供可信任區網或受控管理通道使用，絕不做 WAN 連接埠轉送，也不建立公開 DNS 指向它。

安全基線

  • 首次登入會用到 admin@example.com／changeme；這是公開預設值，登入後必須立即更改電子郵件與密碼。
  • TCP 81 是管理面，不可公開到網際網路。不要在路由器建立 81 的 WAN 轉送，也不要把它當成一般 Proxy Host 對外發布。
  • 網域、公私有 IP、密碼、DNS API Token、憑證私鑰及完整記錄都視為敏感資料；範例、截圖與求助貼文一律改寫或遮罩。
  • 只有確定需要時才公開 80／443。採 Tunnel 時，依該方案縮小防火牆入口，而不是同時保留不必要的直接公開。
不要把真實密碼或 Token 貼入教學筆記。密碼管理器只能保存於你信任的保管庫；DNS Token 應使用供應商可提供的最小權限。

檢查可以繼續的條件
Home Assistant 類型準備走 add-on 路線時，為 HAOS 或 Supervised

觀念排錯

問題一：以為建立 Proxy Host 就會自動建立 DNS

NPM 不替你註冊網域或自動完成公開 DNS。先確認 DNS 與入口策略，再建立對應主機。

問題二：把 TCP 81 當成公開網站入口

81 是管理介面。移除任何 WAN 轉送或公開代理規則，只從可信任區網或受控通道管理。

問題三：80 或 443 已被其他 add-on 使用

同一主機位址與協定不能由兩個服務同時監聽同一連接埠。先盤點衝突，不要在不理解影響時停用既有服務。

問題四：認為 HTTPS 等於後端已安全

HTTPS 保護傳輸，不會修補弱密碼、過期軟體或錯誤權限。回到後端逐項完成登入、更新與最小權限。

問題五：同時啟用 Tunnel 與不必要的 WAN 轉送

這會留下第二個入口。依你選定的架構逐一核對防火牆與路由器，不要保留用不到的公開路徑。

常見問題

NPM 會取代 Home Assistant 嗎？
不會。NPM 是反向代理入口；Home Assistant 仍是獨立的後端服務。
沒有網域也能先安裝嗎？
可以先在可信任區網完成安裝與帳號加固，但正式的網域代理與公開憑證流程仍需要相應的名稱解析與驗證條件。
用了 Tunnel，還需要 NPM 嗎？
取決於你的路由需求。Woow 文件提供 Tunnel 把流量送到 NPM、再由 NPM 做內部路由的做法；如果沒有多主機路由需求，應先評估是否需要多一層。
可以把管理介面放到公開網域嗎？
本教學不建議，也不提供這種做法。TCP 81 應留在可信任區網或受控管理通道，不可直接公開。
