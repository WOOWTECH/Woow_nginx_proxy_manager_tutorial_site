Chapter 4

The admin interface and the core objects

Get clear on how the Dashboard, Hosts, certificates, access lists and users relate to each other, and only then create your first reverse proxy rule.

What the Dashboard shows

The Dashboard you land on after logging in is a summary of host objects, not a traffic monitoring dashboard. The Nginx Proxy Manager 2.12.4 interface the Woow add-on currently uses shows count cards for Proxy Hosts, Redirection Hosts, Streams and 404 Hosts, according to your permissions; click a card to open the matching list.

Confirm security first: if you can still log in with admin@example.com / changeme, change the email and the password immediately. The admin interface on 81/tcp belongs only on a trusted LAN or a protected management channel, and must never be exposed directly to the public internet.

A map of the core objects

NPM splits settings with different purposes into separate objects. Pick the right type before you create anything and troubleshooting later gets much easier.

How the Hosts menu is split

Proxy Hosts are the objects this tutorial uses most: one 80/443 entry point can route to different internal services according to the domain in the request. Redirection Hosts only send the browser somewhere else; 404 Hosts exist to explicitly refuse a given name; Streams handle non-HTTP TCP/UDP traffic.

Enabled/Disabled in a list tells you whether that object is active, not that the upstream service is healthy. The counts on the Dashboard are no substitute for a real connection test either.

Certificates and Access Lists

SSL Certificates and Access Lists are both objects you can reference more than once. A certificate that covers the right name can be assigned to a Proxy Host, and one Access List can be applied to several Proxy Hosts. Before you change a shared object, work out which services it affects.

Sensitive data: domains, certificates and private keys, DNS API tokens and Access List passwords must never be pasted into a public issue, a screenshot or an unredacted document. DNS Challenge certificate data is a high-privilege secret: apply least privilege and limit which DNS zones it can act on.

Users and Audit Log

Users manages who can log in to NPM and with what permissions; it is not the same as an Access List, which protects the proxied site instead. The official feature list also names user management, permissions and the Audit Log. Use individual accounts for day-to-day work, and avoid having several people share one administrator password.

The Audit Log is there to look back at admin actions; it is not the Nginx access or error log. Before you export or share any record, redact accounts, domains, public and private IPs, certificate details, request paths and full logs.

A safe tour, step by step

  1. Confirm the admin entry point

    Open the Home Assistant add-on Web UI from your LAN, or use a protected management channel. Check that the router does not forward external port 81 to NPM.

  2. Confirm your own account

    From the personal menu at the top right, confirm the email is no longer the default and the password has been changed to one that is unique and long enough.

  3. Open the lists in order

    Browse Hosts, SSL Certificates, Access Lists, Users and the Audit Log only. Do not add, delete or disable any existing object.

  4. Write down the dependencies

    For any Proxy Host you plan to change, record the names of the certificate and the Access List it references; in your notes, replace real domains, IPs and accounts with placeholders.

The order to create objects in

For a first build, work through "confirm the upstream service → create the DNS record → create the Proxy Host → test from inside and outside → request and assign the certificate → apply an Access List if you need one". DNS and the Proxy Host must use the same fully qualified domain name, or NPM cannot pick the right rule from the Host header.

Certificates, access rules and Proxy Hosts are stored as separate objects; before you delete anything shared, check what references it and keep a backup you can restore from.

Admin security boundaries

  • The public service entry point is usually 80/443; 81 is the admin port, and neither the router nor a cloud firewall may expose it.
  • Do not make the NPM admin page itself your first public Proxy Host; for remote administration, prefer a VPN or a management channel with authentication.
  • When you share a screen or ask for help, redact all real domains, public and private IPs, passwords, tokens, certificate contents and logs.
  • The Advanced field feeds straight into Nginx behavior; leave it empty when you have nothing to base it on, and never paste in a config snippet of unknown origin.

FAQ

Do the Dashboard numbers prove the proxy works?
No. The numbers summarize how many objects exist; you still have to resolve the domain for real and test the response with a browser or curl.
Can an Access List account log in to NPM?
Do not treat the two as the same kind of account. Users are the admin interface users; the HTTP Basic Authentication in an Access List protects a specific Proxy Host.
Can I expose 81 and protect it with a strong password?
We do not recommend it, and it falls outside this tutorial's security boundaries. Port 81 must never be exposed directly to the public internet; come in from a trusted LAN, a VPN or a protected management channel instead.
Can I delete a Host I do not recognize?
No. First find out who created it, which certificate it references and what it is for, and make a backup; if you are still unsure, leave it as it is.
Why does my screen differ from the latest official screenshots?
The Woow add-on's README and config currently state upstream NPM 2.12.4, while the official project keeps updating. Field names or the layout may differ, so go by the version you installed and the upstream docs.
