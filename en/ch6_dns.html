Chapter 6

DNS 與網域解析

用 A 或 CNAME 記錄把名稱帶到正確入口，釐清公開 IP、NAT，以及 Cloudflare Proxied 與 DNS-only 的差異。

DNS 在代理路徑的位置

DNS 負責把網域名稱轉成用戶端可連線的目的地；它不保存 NPM 的上游連接埠，也不會替路由器建立 NAT。傳統公開模式的完整路徑是「網域 → 公開 IP → 路由器 80／443 NAT → NPM → 內部服務」。

app.example.net
  └─ DNS → [路由器公開 IP]
       └─ TCP 80/443 NAT → [NPM 位址]
            └─ Proxy Host → [內部服務位址]:[服務連接埠]
安全邊界：管理埠 81 不屬於這條公開路徑，不可建立公網 NAT。預設 admin@example.com／changeme 也必須在任何公開服務前立即更改。

先盤點入口資料

資料從哪裡確認用途
完整網域你的 DNS 供應商控制台同時填入 DNS 與 NPM Domain Names
路由器 WAN 位址路由器狀態頁判斷是否持有可被網際網路連入的位址
外部觀測位址可信任的外部查詢方式和 WAN 位址比對，協助辨識上游 NAT
NPM 區網位址Home Assistant 與路由器租約NAT 的內部目的地
DNS 目標主機名既有動態 DNS 或平台文件需要以 CNAME 指向另一名稱時使用

以上全是敏感資料。公開筆記請改用 app.example.net、[公開 IP]、[內部 IP] 等代號；密碼、DNS API token、憑證與完整 log 不得附上。

A 與 CNAME 怎麼選

記錄類型值代表什麼適合情境注意事項
AIPv4 位址直接把名稱指向公開 IPv4公開 IP 變動時要同步更新記錄
CNAME另一個完整主機名稱多個子網域共用同一個動態 DNS 名稱不能把 URL、路徑或 IP 當成 CNAME 目標

無論選 A 或 CNAME，DNS 記錄都不包含 :81、:443 或任何路徑。服務連接埠由用戶端協定、NAT 與 NPM 規則處理。

建立 A 或 CNAME 記錄

  1. 選擇測試名稱

    使用獨立子網域，例如 app.example.net，避免直接改動仍在使用的正式記錄。

  2. 決定記錄類型

    若你有可維護的公開 IPv4，建立 A 記錄；若已有受維護的目標主機名，建立 CNAME 指向該名稱。

  3. 填入名稱與目標

    A 的內容是公開 IPv4；CNAME 的內容是另一主機名稱。不可填 NPM 上游的內部 IP，除非這本來就是僅供內部 DNS 使用的設計。

  4. 選擇 TTL 與代理狀態

    TTL 控制解析器可快取記錄多久。若使用 Cloudflare，再依本章後段決定 Proxied 或 DNS-only，不要把橘雲當成單純外觀選項。

  5. 儲存後查詢

    從內網與行動網路分別查詢，保存「是否符合設計」的結果即可；分享時遮罩真實網域與 IP。

公開 IP 與 NAT

傳統 NPM 對外模式需要可從網際網路抵達的入口。路由器取得的 WAN 位址如果是 RFC 1918 私有範圍，或落在供共享位址使用的 100.64.0.0/10，就不是可直接從公網路由到你路由器的 IPv4；即使看似公開，WAN 與外部觀測結果不同也可能代表雙層 NAT、CGNAT 或其他上游轉換，需向 ISP 或網路管理者確認。

公開 IP 可能是動態的。若它變更而 A 記錄沒有更新，用戶端會前往舊位置；可以使用可信任的動態 DNS 更新機制，但其 API token 必須採最小權限並安全保存。

設定 NAT 與防火牆

  1. 固定 NPM 的區網位置

    在路由器以 DHCP 保留等方式，避免 Home Assistant 位址改變後 NAT 指向錯誤。

  2. 建立必要轉送

    傳統模式把外部 TCP 80 導向 NPM 的 80，外部 TCP 443 導向 NPM 的 443。不要建立外部 81 到內部 81 的規則。

  3. 檢查上游設備

    若 ISP 數據機與自有路由器都執行 NAT，必須釐清每一層；不確定時不要把設備設成全開放或 DMZ。

  4. 從真正外網測試

    關閉手機 Wi-Fi 後測試測試網域。區域網路成功不代表公網 NAT 成功。

若採 Cloudflare Tunnel，資料路徑與 DNS 目標不同，而且通常不需要路由器轉送 80／443；不要同時照抄兩種拓撲。Tunnel 架構在第 8 章說明。

Cloudflare Proxied 與 DNS-only

狀態DNS 查詢通常看見HTTP／HTTPS 路徑安全含意
Proxied（橘雲）Cloudflare anycast IP，而非來源站 IP用戶端先到 Cloudflare，再由 Cloudflare 連來源站可隱藏 DNS 中的來源 IP並套用 Cloudflare 功能，但不能取代來源站防火牆與更新
DNS-only（灰雲）A／AAAA 的來源 IP；CNAME 依一般 DNS 鏈解析用戶端直接連來源站不會套用 Cloudflare HTTP proxy 的保護，且會揭露可解析出的來源位址

Cloudflare 官方說明可代理 A、AAAA 與 CNAME 記錄；只有支援的 HTTP／HTTPS 連接埠能透過一般橘雲代理。郵件、驗證記錄及不相容的非 HTTP 服務通常應保持 DNS-only。NPM 的 Stream 也不能因為切成橘雲就自動得到任意 TCP／UDP 代理能力。

解析與生效測試

DNS 更新沒有保證「幾分鐘一定全球生效」。權威伺服器更新、遞迴解析器快取與本機快取都會影響看到新值的時間，TTL 只是控制快取有效期的重要因素之一。

dig A app.example.net
dig CNAME app.example.net
nslookup app.example.net

若是 Cloudflare Proxied 記錄，查到 Cloudflare IP 是預期行為，不能用它判定來源站 A 值是否正確。可把本機結果和指定的可信任遞迴解析器、權威 DNS 結果分開比較；不要在公開回報中貼出真實答案。

測試位置要驗證的事失敗時先查
區域網路內部 DNS 或 hairpin NAT 是否符合設計內外 DNS 答案是否不同
行動網路公開 DNS、ISP 路徑與 NAT公開 IP、CGNAT、80／443 防火牆
HTTP HostNPM 是否命中正確 Proxy HostDomain Names 與實際網址是否一致

常見問題

A 記錄要填 NPM 的內部 IP 還是公開 IP？
公開 DNS 的傳統 NAT 架構通常填路由器的公開 IP，再把 80／443 轉送到 NPM。只有受控內部 DNS 的 split DNS 設計才會對內回覆內部位址。
CNAME 可以填 IP 或完整 URL 嗎？
不可以。CNAME 的目標是另一個主機名稱；IPv4 應使用 A，URL 路徑則不屬於 DNS 記錄內容。
Cloudflare 橘雲會代理管理埠 81 嗎？
不應這樣設計。81 是 NPM 管理埠且不可公開；一般 Cloudflare HTTP proxy 也只支援官方列出的連接埠。
改 DNS 後要等多久？
沒有適用所有環境的固定時間。請查權威答案、TTL 與各層快取，而不是只等待或反覆重建記錄。
沒有公開 IPv4 就完全不能用 NPM 嗎？
NPM 仍可在內網使用。若要對外，可評估 ISP 提供可入站位址、正確規劃 IPv6，或使用 Cloudflare Tunnel 等出站式方案；不要為繞過 CGNAT 而公開 81。
