Chapter 6

DNS and domain resolution

Use an A or CNAME record to take a name to the right entry point, and get clear on public IPs, NAT, and the difference between Cloudflare Proxied and DNS-only.

Where DNS sits in the proxy path

DNS turns a domain name into a destination the client can connect to. It does not hold NPM's upstream port, and it does not create NAT on your router for you. The full path in the traditional public setup is "domain → public IP → router 80/443 NAT → NPM → internal service".

app.example.net
  └─ DNS → [路由器公開 IP]
       └─ TCP 80/443 NAT → [NPM 位址]
            └─ Proxy Host → [內部服務位址]:[服務連接埠]
Security boundary: admin port 81 is not part of this public path, and must never get a public NAT rule. You must also change the default admin@example.com / changeme immediately, before you publish any service.

All of this is sensitive data. In notes you make public, use placeholders such as app.example.net, [公開 IP] and [內部 IP]; passwords, DNS API tokens, certificates and full logs must not be attached at all.

Choosing between A and CNAME

Record typeWhat the value meansBest forWatch out
AAn IPv4 addressPointing a name straight at a public IPv4When the public IP changes, the record has to be updated with it
CNAMEAnother fully qualified domain nameSeveral subdomains sharing one dynamic DNS nameA URL, a path or an IP cannot be the target of a CNAME

Whether you pick A or CNAME, a DNS record never contains :81, :443 or any path. The service port is handled by the client's protocol, by NAT and by your NPM rules.

Create an A or CNAME record

  1. Choose a test name

    Use a separate subdomain, such as app.example.net, so you avoid changing a production record that is still in use.

  2. Decide on the record type

    If you have a public IPv4 you can keep up to date, create an A record. If you already have a maintained target hostname, create a CNAME pointing at that name.

  3. Fill in the name and the target

    The content of an A record is a public IPv4; the content of a CNAME is another hostname. Do not enter NPM's internal upstream IP unless the design was internal-DNS-only from the start.

  4. Choose the TTL and the proxy status

    TTL controls how long a resolver may cache the record. On Cloudflare, use the later part of this chapter to decide between Proxied and DNS-only; do not treat the orange cloud as just a cosmetic option.

  5. Save it, then query it

    Query from the LAN and over mobile data separately, and keep only the result of "does this match the design". Redact the real domain and IPs when you share anything.

Public IP and NAT

The traditional public-facing NPM setup needs an entry point the public internet can reach. If the WAN address your router gets is in the RFC 1918 private ranges, or falls inside 100.64.0.0/10, the range reserved for shared addresses, it is not an IPv4 the public internet can route straight to your router. Even when the address looks public, a WAN address that differs from the externally observed one can mean double NAT, CGNAT or another upstream translation, and you need to confirm that with your ISP or network administrator.

A public IP can be dynamic. If it changes and the A record does not, clients go to the old location. You can use a trusted dynamic DNS updater, but its API token must follow least privilege and be stored securely.

Set up NAT and the firewall

  1. Pin NPM's LAN address

    Use a DHCP reservation on the router, or something equivalent, so NAT does not end up pointing at the wrong place once the Home Assistant address changes.

  2. Create the necessary port forwarding rules

    The traditional setup sends external TCP 80 to NPM's 80 and external TCP 443 to NPM's 443. Do not create a rule from external 81 to internal 81.

  3. Check the upstream equipment

    If both the ISP modem and your own router perform NAT, work out what every layer does. While you are unsure, do not set a device wide open or into a DMZ.

  4. Test from a genuinely external network

    Turn off Wi-Fi on your phone and test the test domain over mobile data. Success on the LAN says nothing about whether public NAT works.

With Cloudflare Tunnel the data path and the DNS target are different, and you usually do not need router forwarding for 80/443 at all; do not copy both topologies at once. Chapter 8 covers the Tunnel architecture.

Cloudflare Proxied vs DNS-only

StatusWhat a DNS query usually returnsHTTP/HTTPS pathSecurity implication
Proxied (the orange cloud)A Cloudflare anycast IP, not the origin server's IPThe client reaches Cloudflare first, and Cloudflare connects to the origin serverCan hide the origin IP in DNS and apply Cloudflare features, but it is no substitute for the origin server's own firewall and updates
DNS-only (the grey cloud)The origin IP from the A/AAAA record; a CNAME resolves down the normal DNS chainThe client connects to the origin server directlyNone of the Cloudflare HTTP proxy protections apply, and it exposes an origin address anyone can resolve

Cloudflare's documentation states that A, AAAA and CNAME records can be proxied, and that only the supported HTTP/HTTPS ports go through the ordinary orange-cloud proxy. Mail, verification records and incompatible non-HTTP services should normally stay DNS-only. Switching an NPM Stream to the orange cloud does not automatically give it arbitrary TCP/UDP proxying either.

Resolution and propagation tests

A DNS update carries no guarantee that it "definitely goes global within a few minutes". The authoritative server's update, recursive resolver caches and your local cache all affect when you see the new value, and TTL is only one of the important factors controlling how long a cache stays valid.

dig A app.example.net
dig CNAME app.example.net
nslookup app.example.net

For a Cloudflare Proxied record, getting a Cloudflare IP back is the expected behavior, and you cannot use it to judge whether the origin server's A value is right. You can compare your local result separately against a named trusted recursive resolver and against the authoritative DNS answer; do not paste the real answers into a public report.

FAQ

Should the A record hold NPM's internal IP or the public IP?
In the traditional NAT architecture with public DNS it usually holds the router's public IP, and 80/443 are then forwarded to NPM. Only a split DNS design, on internal DNS you control, answers with an internal address on the inside.
Can a CNAME hold an IP or a full URL?
No. A CNAME's target is another hostname; use an A record for IPv4, and a URL path is not part of a DNS record at all.
Does the Cloudflare orange cloud proxy admin port 81?
That is not a design you should build. Port 81 is NPM's admin port and must not be exposed; the ordinary Cloudflare HTTP proxy also only supports the ports listed in the official documentation.
How long do I have to wait after changing DNS?
There is no fixed time that applies to every environment. Check the authoritative answer, the TTL and the caches at each layer, rather than just waiting or rebuilding the record over and over.
Without a public IPv4, is NPM unusable altogether?
NPM still works on the LAN. To go public, you can look at an inbound-capable address from your ISP, at planning IPv6 properly, or at an outbound approach such as Cloudflare Tunnel; do not expose 81 to get around CGNAT.
