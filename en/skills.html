WoowTech · Nginx Proxy Manager Skill Handbook

Teach an AI Agent to operate NPM without handing over uncontrolled access

A good Skill is not a set of magic commands. It is a workflow you can repeat, audit and reverse. This handbook uses six patterns so the agent can help you take stock of your assets, track certificates, audit access, verify backups, diagnose logs and automate safely.

First, be clear: a pattern is not a ready-made tool

The "Skill patterns" on this page are reusable SOPs: they define the inputs, the allowed data sources, the analysis steps, the output format and the safety gates. You can write one into the Skill or instruction file your agent supports, or use it as a manual runbook.

This page does not recommend any unvetted third-party Skill package. No invented repos, download counts or star counts. The Nginx Proxy Manager website, the official docs and the official GitHub project are sources you can check product behavior against; the agent, backup tool, monitoring platform and third-party integrations you actually adopt are still yours to verify for version, origin and permissions.

Evidence sources and the API line

Before every run, the agent has to identify the NPM version and the deployment option. The NPM web front end calls an interface, but the paths and the schema can change between versions, so an endpoint from an article online is not a stable public API. A Skill may call it only when the official source code for that version, the actual schema, or an integration document you approved can verify the method, the fields, the response and the authorization; otherwise fall back to read-only web-interface instructions or an approved data export.

Six repeatable Skill patterns

1. NPM asset inventory

Default permissions: read-only · Suggested frequency: daily or weekly

Pull Proxy Hosts, Redirection Hosts, Streams, Access Lists, certificates and NPM users into one inventory, so you know what is exposed, where it forwards to, and who can administer it.

  • Inputs: the approved NPM instances, the environment labels and the read-only data sources.
  • Outputs: resource ID and name, domain or port, backend, TLS, Access List, enabled state and the time the data was taken.
  • Checks: duplicate domains, port conflicts, public hosts with no certificate, orphaned Access Lists and unknown owners.
  • Never: an inventory run must not fix, disable or delete anything along the way.

2. Certificate expiry watch

Default permissions: read-only · Suggested frequency: daily

Grade by days to expiry. Do not stop at the date: confirm domain resolution, the names the certificate covers, the hosts using it and any recent renewal errors as well.

  • Outputs: the 7/14/30-day thresholds, SANs, issuer, referencing hosts and renewal prerequisites.
  • Alert deduplication: build the event key from the certificate identifier and the expiry date, so you do not raise a new event every day.
  • Safety: never output a private key or a DNS API token; cap the number of automatic retries so you do not hit the CA rate limit.

3. Access List and account audit

Default permissions: read-only · Suggested frequency: weekly and after every change

Check the NPM admin users, the source rules on an Access List, and the HTTP Basic Authentication accounts inside an Access List separately, so you never confuse the three.

  • Checks: over-broad CIDRs, rule order, lists that are never applied, shared admin accounts, disabled state and who is responsible for each one.
  • Outputs: the evidence, the risk level, the affected hosts, the suggested diff and the risk of locking yourself out.
  • Limits: never read out a password; confirm a backup admin path before you tighten a rule.

4. Backup and restore verification

Default permissions: read-only on the backup store · Suggested frequency: verify after every backup, drill every quarter

Work out from the deployment option which database, configuration and certificate data sits in persistent storage, check the encryption, the checksums, the retention and the off-site copy, then run a restore drill in an isolated environment.

  • Passing conditions: it decrypts, the contents are complete, the version is compatible, the isolated instance starts, and a representative host configuration is readable.
  • Outputs: RPO / RTO, the last successful run, the checksum results, what is missing and the evidence from the drill.
  • Never: overwrite production data before you have confirmed which environment you are in and taken a snapshot.

5. Log diagnosis

Default permissions: read-only on logs · Triggers: 502, 504, TLS or redirect events

Build the timeline first, then split it into layers: DNS, the entry point, NPM, the network and the backend. A diagnosis has to keep "facts you observed" apart from "hypotheses still to verify".

  • 502: check the upstream address, port, scheme, name resolution, TLS and backend refusals first.
  • 504: compare backend response times, packet loss and timeouts; do not use a larger timeout to paper over the root cause.
  • Privacy: before you output anything, redact Authorization headers, cookies, tokens, personal data in query strings and internal secrets.

6. Safe change automation

Default permissions: read-only; a single short-lived write permission needs separate approval

Turn "detect, propose, approve, execute, verify, roll back" into a state machine. Handle one explicitly named resource at a time, and use an idempotency check so nothing is created twice.

  • Proposal: show the resource identifier, the before-and-after diff, the impact, the dependencies, the rollback and how it will be verified.
  • Approval: the confirmation text has to bind the target, the diff hash and an expiry; an old approval must never be applied to a new diff.
  • Execution: use only a verified interface and least privilege; read the value back and compare it right after the write.
  • Failure: stop the rest of the batch, keep the evidence, roll back to the approved plan, and never widen the fix on your own.

Every Skill needs a safety contract

Contract itemMinimum requirement
ScopeList the allowed NPM instances, resource types, domains and environments; anything not listed is denied by default.
Identity and permissionsA separate agent identity, least privilege and short-lived secrets; never share your admin cookie.
Data handlingSecrets stay out of prompts, out of logs and out of external models; redact a report before you store it.
Change gatePreview the diff, the impact and the rollback, and require explicit human confirmation; deletion and restore need a stronger confirmation that names the target.
AuditabilityRecord who, when, on which resource, under which approval, and with what result; do not record passwords or tokens.
Stop conditionsStop immediately on a version mismatch, an unverifiable schema, a failed backup, target drift or a failed verification.
High-risk actions must not be fully automated: deleting a Proxy Host, a certificate or a user, overwriting the database, restoring into production, changing Access Lists in bulk, and upgrading a major version all need your approval and a rollback point you keep.

Four automation levels, starting read-only

LayerWhat the agent can doCondition to move up
L0 AdviceRead the redacted data you provide and produce a list and the steps to follow.The output is stable, with no invented fields or tools.
L1 Read-onlyScheduled inventory, expiry checks, log queries and alerts.Sources are verified, permissions are isolated, sensitive data is redacted and the false positives are acceptable.
L2 Approved writesMake a previewed, reversible change to a single resource.It passes in a test environment, the diff is bound to the approval, and post-write verification and a rollback drill are done.
L3 Low-risk auto-remediationHandle only pre-approved, narrowly scoped, idempotent events.There is an error budget, a rate limit, a kill switch and human on-call; high-risk actions stay excluded.

A portable Skill spec template

File names and metadata formats differ from one agent to the next, so the template below is neutral and does not stand for any particular product's installation format:

name: npm-certificate-auditor
purpose: take a read-only inventory of NPM certificates and report on them by expiry date and reference

inputs:
- NPM instance identifier and environment label
- a verified, version-matched, read-only way to get the data
- alert thresholds: 7, 14, 30 days

preflight checks:
1. Verify the target instance, the version, the deployment option and the read-only permissions
2. Verify the interface schema; stop if you cannot verify it, and never guess an endpoint
3. Confirm the output location cannot leak secrets

steps:
1. Fetch the certificate metadata and the hosts that reference each certificate
2. Compute the days to expiry, and check the domain names and any recent renewal errors
3. Grade against the thresholds and produce a report carrying the data time and the evidence
4. Redact tokens, cookies, private keys and any unnecessary personal data

outputs:
- a summary, the risk items, the evidence and the suggested manual handling
- never request, renew, delete or reassign a certificate directly

stop conditions:
- the version or the schema does not match
- the response is missing a required field
- the target is not an approved instance
- fetching the data would require elevated permissions

Pre-adoption checklist

  • You can point to the verified source behind every data field, rather than the agent's guess.
  • The agent has its own least-privilege identity; its secrets live in an approved secret manager and can be rotated.
  • Every inventory, certificate, Access List, backup and log report states which instance it came from and when the data was taken.
  • Your test data covers API failures, version drift, partial responses, repeated runs and timeouts.
  • Every write has a concrete diff, human approval, post-write verification, an audit record and a rollback plan.
  • Deletion, production restores and bulk permission changes are never in scope for unattended automation.
  • You have set up a kill switch, and you know who takes over when the agent fails.
Run L1 for at least one full operations cycle first. Once you have confirmed that the reports are accurate, that nothing leaks and that false positives stay manageable, pick one low-risk, reversible task and move it to L2. Do not hand the agent every administrative right at once.
