Chapter 5

Create your first Proxy Host

Use one test domain to forward the HTTP requests NPM receives to an existing internal web service, then verify all three layers one at a time: DNS, NPM and the upstream.

Understand the request path first

The Proxy Host path is "client → the NPM entry point DNS points at → NPM matches the domain against its rules → the internal web service". NPM does not create DNS for you, and it does not automatically open NAT on your router; every layer has to be set up correctly on its own.

app.example.net → NPM 的 80/tcp → http://[內部服務位址]:[服務連接埠]

example.net and everything in square brackets are placeholders. Real domains, public and private IPs, passwords, certificates and logs are all sensitive data; redact them in your notes and in anything you post when asking for help.

Create the Proxy Host

  1. Open Proxy Hosts

    In NPM, go to Hosts → Proxy Hosts, then click Add Proxy Host. Do not edit an existing rule with a similar name.

  2. Enter the domain

    Put your test fully qualified domain name in Domain Names. Keep the real value out of public screenshots and support tickets.

  3. Set the upstream

    Choose the Scheme that matches how the upstream actually runs, then fill in a Forward Hostname / IP and Forward Port that NPM can reach.

  4. Choose the basic switches

    For an ordinary service you can turn on Block Common Exploits. Turn on Websockets Support only when the upstream really uses WebSocket; leave caching off on the first pass.

  5. Leave SSL alone for now

    So that you can troubleshoot layer by layer, set the SSL tab to None and leave Advanced empty. Chapter 7 covers requesting a certificate and forcing its use.

  6. Save it and write it down

    Click Save and confirm the new row reads Enabled. Record only an identifier, the time you created it and what it is for; never copy sensitive values.

Trade-offs on the basic switches

Cache Assets can change how dynamic content refreshes, so keep it off for the first test. Block Common Exploits is an extra rule set NPM provides, but it does not replace upstream updates, authentication and minimal exposure. Websockets Support handles upgraded connections; an ordinary website does not need to turn it on in the hope of being "faster".

Do not paste Advanced config: the official interface explicitly reserves it for advanced Nginx configuration. Leave it empty until you have verified what the upstream needs and what each directive does.

Confirm DNS lands on NPM

Once the Proxy Host is saved, the name still has to resolve to the right entry point. In the traditional public-facing setup, public DNS usually points at the router's public IP and NAT sends 80/443 on to NPM; for a LAN-only test you can also use an internal DNS override that you control. Chapter 6 covers how to do it.

dig +short A app.example.net
nslookup app.example.net

The answer should match your design, rather than some fixed IP you expect blindly. A Cloudflare Proxied record answers with a Cloudflare IP and does not show the origin server IP; only DNS-only answers with the record's target directly.

Test your first Host layer by layer

  1. Test the upstream first

    From a device that stands in for NPM's position on the network, open the upstream URL and confirm the protocol, host and port really respond. Do not paste a full URL containing a token into your test record.

  2. Then check DNS

    Use dig or nslookup to confirm the test device gets the entry point you expect. If the answer is wrong, fix DNS first; do not keep changing the Proxy Host.

  3. Test the HTTP headers

    Run curl -I http://app.example.net. The status code may vary with the upstream; what matters is that the request reached the service you expected, rather than treating any particular status code as the sole measure of success.

  4. Verify the features in a browser

    Open the test domain and check login, static assets and live features. If the application asks for trusted proxies or an external URL, change those only as that application's official documentation says.

Security check before going live

  • NPM's default admin@example.com / changeme must have been changed immediately.
  • External NAT or the firewall must not open admin port 81; in the traditional setup you send only the necessary 80/443 to NPM.
  • Do not expose an admin backend that was only ever meant for the LAN; when it needs extra protection, plan an Access List, application authentication or a VPN first.
  • Until SSL is in place, do not enter passwords or other sensitive data over the public internet. Use only test pages that hold no sensitive data for HTTP testing.
  • Redact domains, public and private IPs, passwords, DNS tokens, certificates and full logs before you share them.

FAQ

Does Domain Names take a full URL?
No. Enter the fully qualified domain name, for example app.example.net; do not add http://, a path or a port.
Can Forward Hostname / IP be localhost?
Only when the upstream really runs in the same runtime environment as NPM can that even be correct. Inside the Woow add-on, 127.0.0.1 points at the add-on itself; it does not automatically stand for the Home Assistant host or any other device on the LAN.
Does the first Host need WebSocket turned on?
No. Turn it on only when an upstream feature needs WebSocket; it is not a general performance switch.
Why leave SSL until later?
Verifying DNS, NPM and the upstream path layer by layer first helps keep certificate challenge errors from getting mixed up with proxy errors. You must still finish HTTPS before you enter real sensitive data.
Does a Public Access List mean the service is safe to publish?
No. It only means no NPM Access List is applied; the application itself still needs updates, authentication and an appropriate security policy.
