Chapter 12

Common errors and full diagnosis

Take the path apart from the client onward: DNS, the external entry point, NPM, the upstream, TLS and Cloudflare. Prove one layer at a time and change one thing at a time, so you stop guessing back and forth between DNS, the router and the Proxy Host.

Map every layer a request passes through

"The site won't open" is not a diagnosis. Work out which path the request takes, then find the last layer that succeeded and the first layer that failed. If you use Cloudflare Tunnel, the path is not the same as traditional port forwarding, and you cannot carry the same assumptions across.

LayerWhat to proveTypical evidence
1. ClientWhether the problem only happens in one browser or on one networkA private window, another device, mobile data
2. DNSWhether the name resolves to the public entry point you expectThe A/AAAA/CNAME answer and the resolver
3. External entry pointWhether 80/443, NAT or the Tunnel can reach NPMA timeout, a refused connection, a Cloudflare error page
4. NPMWhether the right Host is enabled and can load its configHost status, the add-on log, the HTTP status code
5. UpstreamWhether NPM can reach the service with the right scheme/IP/portThe result of a direct connection, connection refused/timeout
6. Application and TLSWhether the application path, WebSocket and the certificate chain are correctA 404, a 101 handshake, the browser's certificate details
Port 81 stays private even while troubleshooting: the admin interface stays on a trusted network segment. If you have not yet changed admin@example.com / changeme, update the account and the password immediately before you do anything else; never forward 81 to the public internet on the grounds that it is a "temporary test".

Gather evidence that is safe and comparable

  1. Narrow the time window

    Write down when it happened, the time zone, the rewritten stand-in for the test URL, the client network, and the last time it worked. Reproduce one request at a time.

  2. Record symptoms, not secrets

    Keep the HTTP status code, the error type and the few log lines that relate to it; redact domains, public and private IPs, Authorization, Cookie, passwords, DNS API tokens, certificate contents and query parameters.

  3. Set up a control comparison

    Compare a direct connection to the upstream from the LAN, a connection through NPM from the LAN, and a connection through the public entry point from outside. If you use Cloudflare, compare before and after the Tunnel or the proxy as well, but do not switch production DNS on a whim.

  4. Change one thing at a time

    Record the original value before you save. Do not change DNS, the router port, Forward Scheme and the certificate at once, or you will not know which one made the difference.

A full log usually contains hostnames, IPs, URLs, User-Agent strings or other identifying data. When you ask for support, paste only the smallest fragment you need; if a token, a password or a private key has already been exposed, deleting the post is not enough — rotate it immediately.

DNS: confirm where the name goes

  1. Query the resolver you are actually using

    Look up A, AAAA or CNAME from the LAN and over mobile data separately. Redact the full domain and the IPs before you record the result. Different answers inside and outside can mean split DNS, but they can equally mean a cache or a wrong record.

  2. Check the answer against your architecture

    With traditional NAT, the A/AAAA answer should lead to your public entry point; a Cloudflare Proxied record usually answers with a Cloudflare address; a Tunnel's public hostname is routed by Cloudflare. Do not read a Cloudflare IP as an error.

  3. Check for a stray AAAA

    If only IPv6 clients fail, confirm that the AAAA really has a reachable IPv6 entry point behind it. Do not fix the A record alone and overlook that a client may prefer AAAA.

  4. Wait out the TTL and check the authoritative settings

    The local cache is only one layer. Check the record and the TTL your DNS provider currently holds; do not create more variables by deleting and recreating it over and over.

80/443: prove the entry point is reachable from outside

The Woow add-on declares 80/tcp as HTTP, 443/tcp as HTTPS and 81/tcp as Admin. A traditional setup usually forwards only 80/443 to HA; a Cloudflare Tunnel setup does not need the router to forward those ports at all. Start by confirming which one you actually run.

  1. Use a genuinely external network

    Turn off Wi-Fi on your phone and test over mobile data, so NAT loopback does not make an internal result look like external reachability. Record whether you got a timeout, connection refused, a TLS error or an HTTP response.

  2. Traditional NAT: check 80/443

    Confirm that the router rule targets the right HA private IP, that the protocol is TCP, and that the HA address has not changed because of DHCP. Do not create a WAN → 81 rule.

  3. Rule out a port clash or a block further upstream

    If the add-on will not start, check whether another service already holds 80/81/443. If everything from outside times out, also check whether your ISP uses CGNAT or blocks inbound ports.

  4. Tunnel: do not chase NAT at the same time

    Confirm that the cloudflared connector is online and that the public hostname points at an internal service NPM can reach. When a Tunnel fails, opening more router ports is usually not the fix.

Requesting a certificate with HTTP-01 needs the challenge endpoint to be reachable on public port 80; DNS-01 does not require 80 to be open. Do not assume that because you use DNS-01, 443 or the upstream must be fine — those are different layers.

Upstream: taking apart 502 Bad Gateway

A 502 in NPM usually means NPM did receive the request but could not get a usable response from the upstream you configured. Check Forward Scheme, Hostname/IP and Port first; do not start by requesting the public certificate again.

  1. Connect to the service directly from the LAN

    Test the rewritten upstream URL with the scheme and port the service actually uses. If the direct connection fails too, deal with the application, the host firewall or the address the service listens on first.

  2. Rule out the localhost trap

    For an add-on, 127.0.0.1/localhost usually means the container itself, not the HA host or another machine. Use a private address or name that NPM can reach from its own network.

  3. Match the scheme against the port

    Entering an HTTP upstream as HTTPS, or treating an HTTPS port as HTTP, can both fail. Confirm that the service really speaks that protocol on that port.

  4. Read the error from the same moment

    connection refused usually means nothing on that address/port is accepting connections; timed out usually means routing, a firewall or a service that never answered. Keep the error type, and redact the addresses before you share it.

SSL: separate issuance, assignment and client validation

An "SSL error" can arise in more than one place: requesting the certificate, assigning it in NPM, the browser validating it, or NPM's own connection to an HTTPS upstream. Work out which hop the error is on first.

  1. Check the certificate the browser actually receives

    Check that the Subject Alternative Name, the validity dates and the issuing chain match the domain you are on. Record only the fields you need; do not export or share the private key.

  2. Confirm the Proxy Host picked the right certificate

    One wildcard or multi-domain certificate does not mean it was applied to the Host automatically. Check the selection on the SSL tab, Force SSL, and the Host status.

  3. If issuance fails, check the challenge path

    For HTTP-01, check DNS and port 80 from outside; for DNS-01, check the DNS provider, the zone permissions and the least-privilege token. Never paste a token into a log or a support ticket.

  4. Rule out clock and renewal problems

    Confirm that the clock on the HA host is correct, and read the add-on log from around the renewal time. Do not repeat a failed request over and over, or you may run into the CA rate limit.

Do not turn off client certificate validation to make the warning go away, and do not confuse a self-signed certificate problem on the origin with the public-facing Let's Encrypt certificate. Confirm each TLS hop on its own.

Cloudflare: work out which side the error is on

Cloudflare's own documentation states that a 502/504 means Cloudflare could not reach the origin web server, and that the cause can be on the origin or on Cloudflare. Seeing a Cloudflare page does not prove NPM never received the request; cross-check the time, the Ray ID and the origin or Tunnel log.

  1. Tell a Proxy apart from a Tunnel

    A Proxied DNS record (the orange cloud) still generally needs Cloudflare to reach a public origin server; with a Tunnel, cloudflared opens the connection itself. Do not try to fix a Tunnel by adding NAT rules.

  2. Record the error code and the Ray ID

    Keep the time it happened, the Cloudflare error code and the Ray ID; still redact domains and IPs before you send anything. Then read the NPM and cloudflared logs from the same period.

  3. Verify the Tunnel service from the LAN

    Confirm that the service scheme, private IP/hostname and port configured in cloudflared are reachable from the network the connector runs on. If it points at the wrong HTTPS or at 81, fix the service first.

  4. Do not flip to DNS-only blindly

    Switching changes the public path, can expose the origin IP and affects every user. Run that comparison only during an approved maintenance window, when you understand the impact and can undo it.

WebSocket: find the handshake or long-connection problem

When a WebSocket's initial HTTP Upgrade succeeds, you normally see 101 Switching Protocols. Move your attention to the WebSocket only when ordinary pages work and live updates fail, rather than rebuilding the whole Proxy Host.

  1. Test the upstream first

    Confirm the application's WS endpoint, scheme and path. If a direct connection already fails, fix the application first.

  2. Check the NPM option

    Edit the Proxy Host and turn on Websockets Support. The official NPM 2.12.4 template adds the Upgrade, Connection and HTTP/1.1 settings.

  3. Read the handshake and the close code

    Look at the WS request in the browser developer tools: a 403 points at authorization or an origin restriction, a 404 at the path, a 502 at the upstream; if it connects and then drops, look at timeouts and the application log.

  4. Compare layer by layer

    Look at the Cloudflare layer only when it works through NPM on the LAN and fails through Cloudflare; if both fail, stay on NPM and the upstream. Redact URLs, Cookie and message contents before you share a screen.

Logs: read only the lines for one request

The Woow add-on's patch redirects several Nginx access and error logs from files to /proc/1/fd/1, which makes the Home Assistant add-on log an important way in; at the same time config.yaml keeps */logs out of backups. Do not assume the /data/logs of a generic Docker tutorial applies here.

  1. Reproduce one request first

    Note the exact time and the Host you expect, so you are not searching through a mass of background traffic.

  2. Read the HA add-on log

    Find the Nginx, NPM backend, certificate or reload messages from around that time. Decide first whether it is a startup, a config syntax, an upstream or a challenge problem.

  3. Line it up with the application and Tunnel logs

    If NPM has the request and the upstream does not, the problem lies between them; if cloudflared shows a 502 and NPM has no record of it, check the Tunnel's service to NPM first.

  4. Produce a minimal extract

    Keep only the lines you need around the error, and rewrite the real domains, IPs, tokens, passwords, certificates, Cookie and full URLs. Do not upload the whole log.

A status code is a direction, not a root cause. Read it together with "which layer produced it", "whether NPM has a record from the same moment" and "whether the upstream received the request".

FAQ

If I see a 502, should I request the SSL certificate again first?
Usually not. Check the scheme, IP/hostname, port and reachability from NPM to the upstream first. The public-facing certificate and an upstream 502 are different layers.
Does testing over the LAN Wi-Fi prove that port forwarding works?
No. The router may support NAT loopback, which lets an internal test loop back and succeed. Test over a genuinely external connection such as mobile data.
When Cloudflare returns an error, can I switch to DNS-only first?
Do not flip it blindly. It changes the path for every user and can expose the origin IP. Locate the problem with the Ray ID, the time and the NPM or Tunnel log first, and run a reversible test only once it has been approved.
Can I paste the full add-on log into a GitHub Issue?
Not as it is. Cut it down to the smallest time window first, and redact domains, public and private IPs, full URLs, Cookie, Authorization, passwords, DNS tokens and certificate data.
