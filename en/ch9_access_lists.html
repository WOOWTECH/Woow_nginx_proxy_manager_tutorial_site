Chapter 9

Access Lists and access restrictions

Put a gate in front of a Proxy Host with HTTP Basic Auth and Nginx allow/deny IP rules, and understand the limits that NAT, Cloudflare Tunnel, dynamic IPs and Satisfy Any place on it.

An Access List is an extra gate, not a cure-all

An NPM Access List can add HTTP Basic Authentication to one or more Proxy Hosts, and can apply allow/deny rules based on the client IP that Nginx sees. It is a good fit for protecting small tools that have no login of their own, but it does not replace application updates, multi-factor authentication (MFA) or full identity management.

What "done" looks like: you can create an Access List, apply it to a test Proxy Host, and separately verify the unauthorized case, the authorized case and the result from a different source network.
Admin security baseline: change admin@example.com / changeme immediately. Port 81 is only for trusted admin sources and must never be exposed to the public internet; wrapping it in an Access List does not make it safe to publish.

How Basic Auth and IP rules differ

Confirm HTTPS first: the Authorization value in HTTP Basic Auth is not an end-to-end encryption mechanism; only HTTPS at the transport layer keeps those credentials from being read straight off the public internet.

Write down who, from where, and into which service

  1. Pick one test Proxy Host only

    Test against a non-critical service first. Do not apply the Access List to every host at once, and do not touch NPM's admin port 81 yet.

  2. Decide the authentication logic

    Password only, source IP only, both, or either one: the four are completely different. Default to least privilege; when you are not sure, leave Satisfy Any off.

  3. Collect the real source addresses

    Confirm what NPM really sees, using networks you control and redacted logs. Do not take a Cloudflare IP list you found online and use it as a visitor allowlist.

  4. Prepare a rollback plan

    Keep an admin path from your trusted LAN to NPM port 81, and record which Access List each Proxy Host used before. If a rule is wrong, roll back that one host; do not delete a list whose purpose you are unsure of.

Create a Basic Auth list

  1. Add an Access List

    Go to Access Lists → Add Access List and give it a name that identifies its purpose without containing a real domain, a person's name or an internal IP.

  2. Leave Satisfy Any off

    If you want every visitor to enter a password, leave Satisfy Any off to begin with. Once it is on, either the IP rules or the password is enough to get in.

  3. Add Authorization credentials

    On the Authorization tab, create a dedicated password that is unique and long enough. Do not reuse the NPM admin password or an upstream service password, and never put credentials into a domain name, a comment or a screenshot.

  4. Handle the final deny in the Woow version

    The Woow add-on README currently states that it bundles NPM 2.12.4; the upstream Access template for that version ends with deny all. If your list relies on Basic Auth alone, go to the Access tab and add allow all first, so the IP condition permits every source, and let Basic Auth with Satisfy Any off ask for the password. After an interface update, go by what your tests show.

  5. Leave Pass Auth to Host off

    Unless the upstream application explicitly needs to receive the same Authorization header, do not forward the Basic credentials NPM received to the upstream, to avoid conflicts or a wider password exposure.

Treat passwords as secrets: the NPM admin password, the Access List password and upstream passwords must never be reused for one another, and none of them belongs in a public log, a screen recording or a support ticket.

Create allow/deny rules

The official Nginx docs state that rules are checked in the order shown and stop at the first match. The NPM 2.12.4 template also ends with deny all, so the order changes the outcome directly.

  1. Allowlist: allow the trusted CIDR first

    Create one allow entry per fixed source, using the smallest CIDR: /32 for a single IPv4 address, /128 for a single IPv6 address. Never paste a real IP into a public document.

  2. Cover IPv4 and IPv6 together

    Your device may use a different protocol on a different network. An IPv4-only allowlist does not mean IPv6 behaves the way you expect, so you must test from both kinds of connection separately.

  3. Denylist: put deny before allow all

    If what you want is "block a few sources and allow the rest", the order should be the specific deny entries first and allow all after them, because the first matching rule decides the outcome.

  4. Do not widen the range for convenience

    allow all is only for making Basic Auth the real gate, or for sitting after specific deny entries to form a denylist. On its own it gives no IP protection.

Apply it to a Proxy Host and verify

  1. Apply it to the test host only

    Edit the test entry under Hosts → Proxy Hosts, select the list you created in Access List, and save.

  2. Test the unauthorized case

    Use a private window or a client with no cached credentials. Basic Auth should show a login prompt; when the IP does not match you should be refused, not shown the upstream application page.

  3. Test a correct and a wrong password

    Confirm that a wrong password does not get through and the correct one does. Close the test window afterward, so a shared computer does not keep the Authorization state.

  4. Test once from an allowed and once from a denied network

    For example, test from a trusted VPN and over mobile data. Record what kind of source NPM actually sees, without publishing the real IP or a full access log.

  5. Then roll it out one host at a time

    Apply the list one Proxy Host at a time only once the whole test matrix behaves as expected. Keep a rollback path every time, so you do not lock yourself out of every service in one batch.

Do not delete an Access List that is in use: the NPM 2.12.4 interface warns explicitly that the Proxy Hosts attached to it become public once it is deleted. Take stock of what is attached, move each host to the correct list, and verify them one by one.

What Satisfy Any actually loosens

SettingNginx logicExample result
Satisfy Any offsatisfy allWith both IP rules and Basic Auth in place, the source IP and the password both have to pass
Satisfy Any onsatisfy anyA matching source IP means no password is needed; or the IP fails but the correct password still gets in
A common misconception: ticking Satisfy Any does not "add another check", it turns the AND into an OR. Use it only when you specifically need a trusted network segment to skip the password, and record what it affects.

The IP NPM sees may not be the visitor's IP

The Nginx access module decides based on the address the connection came from; it does not automatically treat an arbitrary HTTP header as a trusted IP. When a Cloudflare Tunnel, another reverse proxy, a container network or NAT sits in front, NPM may only see the address of the connector, the proxy or the gateway.

  • Cloudflare Tunnel: the visitor's details can appear in a Cloudflare header, but what an NPM Access List judges by default may still be the source of the cloudflared connection. Do not build an allowlist from visitor public IPs without verifying that first.
  • NAT: several people behind one exit can look like a single IP; allowing it allows the whole exit, not one user.
  • Dynamic IPs: home and mobile data connections change, so a rule can suddenly lock you out, or later allow the old IP to somebody else.
  • Spoofed headers: do not trust CF-Connecting-IP or X-Forwarded-For on the strength of a custom config alone. You have to restrict which proxy sources are trusted at the same time, or a client can forge them itself.
Tunnel recommendation: to control access by real user identity, build an identity policy in Cloudflare Access first, or use the upstream application's own login and MFA. Use an IP allowlist only once you have confirmed what the source address NPM sees actually means.
Basic Auth on the internal hop: if you followed Chapter 8 and cloudflared reaches NPM over HTTP, the Authorization header travels in that unencrypted LAN traffic. The connector and NPM should sit in the same trusted/isolated environment; across an untrusted network, switch to a verifiable HTTPS origin hop or to Cloudflare Access.

When an Access List is not enough on its own

  • Important accounting or management systems: Basic Auth has no native MFA, device trust or fine-grained session management, so keep the application's own authentication.
  • Public APIs and mobile apps: the client may not be able to handle a browser-style Basic Auth prompt, or the Authorization header may already be in use by an API token.
  • Protection against password brute force: an Access List on its own is not a complete rate limit, lockout, anomaly detection or WAF.
  • Auditing per person: a shared IP cannot prove which user it was, and shared Basic credentials give no reliable attribution to a person either.
  • The NPM admin interface: port 81 belongs on a trusted management network, rather than being exposed first in the hope that an Access List will make up for it.

Access List FAQ

Can Basic Auth replace an application's login?
It only fits as a low-complexity extra gate. Important services should keep the application's own accounts, MFA, permissions and audit features.
Does Satisfy Any make things more secure?
No. It changes the condition from "all must pass" to "any may pass", which usually loosens things: either a trusted IP or the correct password is enough to get in.
Can I use Cloudflare's IP ranges as a visitor allowlist?
That only says the request came through Cloudflare, not that it came from a particular visitor. Behind a Tunnel or a proxy, confirm which address NPM actually judges by first; to control access per person, use Cloudflare Access or the application's login instead.
Is a dynamic home IP a good fit for an allowlist?
It carries more risk. A changed IP locks you out, and the old IP can be reassigned to somebody else. A fixed VPN exit or a stable management segment fits better.
Does deleting an Access List delete the Proxy Host with it?
No; the NPM 2.12.4 interface warns that the attached hosts become public. Do not delete it outright: move each host to another list and verify them one by one first.
