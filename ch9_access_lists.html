第 9 章

Access Lists 與存取限制

用 HTTP Basic Auth 與 Nginx IP allow／deny 規則替 Proxy Host 加一道門，並理解 NAT、Cloudflare Tunnel、動態 IP 與 Satisfy Any 帶來的限制。

Access List 是額外門禁，不是萬靈丹

NPM Access List 可以替一個或多個 Proxy Host 加上 HTTP Basic Authentication，也可以依 Nginx 看見的用戶端 IP 套用 allow／deny。它很適合保護本身沒有登入功能的小工具，但不能取代應用程式更新、多因素驗證或完整的身分管理。

本章完成條件：你能建立一份 Access List、套用到測試 Proxy Host，分別驗證未授權、已授權與不同來源網路的結果。
管理安全基線：先立即更改 admin@example.com／changeme。port 81 只允許可信任管理來源，不可公開到 Internet，也不應拿 Access List 包住後就當作可以公開。

Basic Auth 與 IP 規則的差別

方式判斷依據適合主要限制
Basic Auth瀏覽器送出的使用者名稱與密碼沒有登入功能的簡單 Web 服務不是 MFA；部分 App、API 或 WebSocket 用戶端不支援；必須搭配 HTTPS
IP allowlistNginx 實際看到的來源位址固定管理網段、VPN 出口或單一固定 IP住家／行動 IP 會變；NAT 共用身分；經反向代理後可能只看到代理 IP
IP denylist依序封鎖特定位址，再允許其餘來源暫時阻擋已知來源攻擊者可換 IP；不是應用層防護或 WAF
兩者同時satisfy all 或 satisfy any要求雙條件，或讓可信任 IP 略過密碼Satisfy Any 常被誤認為更嚴格，實際上是任一條件通過即可
先確認 HTTPS：HTTP Basic Auth 的 Authorization 內容不是端對端加密機制；只有在傳輸層使用 HTTPS 時才可避免憑證在公網被直接攔讀。

寫下誰、從哪裡、能進哪個服務

  1. 只挑一個測試 Proxy Host

    先對非關鍵服務測試，不要一次把 Access List 套到所有主機，也不要先動 NPM 管理 port 81。

  2. 決定驗證邏輯

    只要密碼、只要來源 IP、兩者都要，或任一即可，四種邏輯完全不同。預設採最小權限；不確定時不要開 Satisfy Any。

  3. 蒐集實際來源位址

    從你控制的網路與已遮罩 log 確認 NPM 真正看見的來源。不要直接把網路搜尋到的 Cloudflare IP 清單當作訪客 allowlist。

  4. 準備回復方式

    保留可信任內網到 NPM port 81 的管理路徑，記錄原本 Proxy Host 使用的 Access List。規則錯誤時只回復該主機，不要刪除不確定用途的清單。

建立 Basic Auth 清單

  1. 新增 Access List

    到 Access Lists → Add Access List，輸入能辨識用途但不含真實網域、使用者姓名或內部 IP 的名稱。

  2. 保持 Satisfy Any 關閉

    若你要每位訪客都輸入密碼，先保持 Satisfy Any 關閉。開啟後，只要 IP 規則或密碼任一通過就能進入。

  3. 新增 Authorization 帳密

    在 Authorization 分頁建立專用、唯一且足夠長的密碼。不要重用 NPM 管理員密碼或上游服務密碼，也不要把帳密放進網域名稱、註解或截圖。

  4. 處理 Woow 版本的最終 deny

    Woow add-on README 目前標示內含 NPM 2.12.4；該版上游 Access 範本最後會加入 deny all。若清單只靠 Basic Auth，請在 Access 分頁先加入 allow all，讓 IP 條件允許所有來源，再由關閉 Satisfy Any 的 Basic Auth 要求密碼。介面升級後仍須以測試結果為準。

  5. 保持 Pass Auth to Host 關閉

    除非上游應用明確需要收到同一個 Authorization header，否則不要把 NPM 收到的 Basic 憑證傳給上游，以免衝突或擴大密碼暴露範圍。

密碼視為機密：NPM 管理密碼、Access List 密碼與上游密碼都不可互相重用，也不可出現在公開 log、瀏覽器錄影或工單。

建立 allow／deny 規則

Nginx 官方說明規則依畫面順序檢查，遇到第一個符合項目就停止。NPM 2.12.4 範本最後另有 deny all，因此順序會直接改變結果。

  1. 白名單：先 allow 可信任 CIDR

    每個固定來源建立一筆 allow，使用最小 CIDR；單一 IPv4 用 /32，單一 IPv6 用 /128。不要把真實 IP 貼到公開文件。

  2. 同時考慮 IPv4 與 IPv6

    你的裝置可能在不同網路走不同協定。只有 IPv4 allowlist 不代表 IPv6 行為符合預期，必須分別從兩種連線測試。

  3. 黑名單：deny 要放在 allow all 前

    若需求是「封鎖少數來源，其餘允許」，順序應是特定 deny 在前、allow all 在後；因為第一個符合規則就決定結果。

  4. 不要用超大網段求方便

    allow all 只適合讓 Basic Auth 成為真正門檻，或放在特定 deny 之後形成黑名單。它本身沒有 IP 保護效果。

需求規則順序Satisfy Any
只有固定 IP 可進，不用密碼allow <可信任 CIDR>，其餘由最終 deny all 擋下關閉；不建立 Authorization 使用者
所有來源都要密碼allow all，搭配 Authorization關閉，要求 IP 條件與密碼都通過
固定 IP 且還要密碼allow <可信任 CIDR>，搭配 Authorization關閉，兩項都要通過
固定 IP 可略過密碼，其他人要密碼可信任 CIDR 搭配 Authorization開啟；這是刻意的繞過，不是更嚴格

套用到 Proxy Host 並驗證

  1. 只套用到測試主機

    編輯 Hosts → Proxy Hosts 的測試項目，在 Access List 選擇剛建立的清單後儲存。

  2. 測試未授權狀態

    使用無痕視窗或沒有快取帳密的用戶端存取。Basic Auth 應顯示登入提示；IP 不符時應收到拒絕，而不是上游應用頁面。

  3. 測試正確與錯誤密碼

    確認錯誤密碼無法通過、正確密碼可通過。完成後關閉測試視窗，避免共用電腦保留 Authorization 狀態。

  4. 從允許與拒絕網路各測一次

    例如可信任 VPN 與行動網路各測試；同時記錄 NPM 真正看到的來源類型，不公開實際 IP 或完整 access log。

  5. 再逐一套用

    只有測試矩陣全部符合預期，才一次一個 Proxy Host 套用。每次都保留回復路徑，避免批次鎖住所有服務。

不要隨意刪除正在使用的 Access List：NPM 2.12.4 介面明確警告，刪除後關聯 Proxy Hosts 會變成公開。請先盤點關聯、改套正確清單並逐一驗證。

Satisfy Any 到底放寬了什麼

設定Nginx 邏輯結果示例
Satisfy Any 關閉satisfy all有 IP 規則也有 Basic Auth 時，來源 IP 與密碼兩者都必須通過
Satisfy Any 開啟satisfy any來源 IP 通過就不必輸入密碼；或 IP 不通過但密碼正確仍可進入
常見誤解：勾選 Satisfy Any 不是「多加一種驗證」，而是把 AND 改成 OR。只有你明確需要可信任網段略過密碼時才使用，並記錄影響範圍。

NPM 看到的 IP 未必是訪客 IP

Nginx 的 access module 依連線來源位址判斷，不會自動把任意 HTTP header 當成可信任 IP。當前面還有 Cloudflare Tunnel、其他 reverse proxy、容器網路或 NAT 時，NPM 可能只看到 connector、代理或閘道的位址。

  • Cloudflare Tunnel：訪客資訊可出現在 Cloudflare header，但 NPM Access List 預設判斷的仍可能是 cloudflared 連線來源。不要未經驗證就拿訪客公網 IP 做 allowlist。
  • NAT：同一出口後的多人看起來可能是同一個 IP；允許它等於允許整個出口，而不是一位使用者。
  • 動態 IP：住家與行動網路會變更，規則可能突然把你鎖在外面，或日後把舊 IP 允許給別人。
  • 偽造 header：不要只新增自訂設定就信任 CF-Connecting-IP 或 X-Forwarded-For。必須同時限制可信任代理來源，否則客戶端可能自行偽造。
Tunnel 建議：若要依真實使用者身分控管，優先在 Cloudflare Access 建立身分政策，或使用上游應用自己的登入與 MFA。IP allowlist 只在你已確認 NPM 實際來源語意時使用。
Basic Auth 的內網段：第 8 章若讓 cloudflared 以 HTTP 連 NPM，Authorization header 會出現在這段未加密的內網流量。connector 與 NPM 應位於同一可信任／隔離環境；跨不可信網路時改用可驗證的 HTTPS 回源或 Cloudflare Access。

哪些情況不要只靠 Access List

  • 重要帳務或管理系統：Basic Auth 沒有原生 MFA、裝置信任與細緻工作階段管理，應保留應用自己的身分驗證。
  • 公開 API 與行動 App：用戶端可能無法處理瀏覽器式 Basic Auth 提示，或 Authorization header 已被 API token 使用。
  • 密碼防暴力破解：Access List 本身不是完整的速率限制、鎖定、異常偵測或 WAF。
  • 依人員稽核：共用 IP 無法證明是哪一位使用者；共用 Basic 帳密也無法提供可靠的個人歸屬。
  • NPM 管理介面：port 81 應留在可信任管理網路，而不是先公開再期待 Access List 補救。

Access List 常見問題

Basic Auth 可以取代應用程式登入嗎？
只適合低複雜度的額外門禁。重要服務應保留應用自己的帳號、MFA、權限與稽核功能。
Satisfy Any 會讓安全性更高嗎？
不會。它把條件從「全部通過」改成「任一通過」，通常是放寬，讓可信任 IP 或正確密碼其中一項即可進入。
可以用 Cloudflare 的 IP 範圍當訪客白名單嗎？
那只代表請求經過 Cloudflare，不代表特定訪客。Tunnel 或代理後應先確認 NPM 實際判斷哪個位址；依人員控管時優先用 Cloudflare Access 或應用登入。
住家動態 IP 適合 allowlist 嗎？
風險較高。IP 改變會把你鎖在外面，舊 IP 也可能重新分配。較適合固定 VPN 出口或穩定的管理網段。
刪除 Access List 會讓 Proxy Host 一起消失嗎？
不會；NPM 2.12.4 介面警告關聯主機會變成公開。不要直接刪除，應先逐一改套其他清單並驗證。
