常見錯誤與完整排查

從用戶端一路拆成 DNS、外部入口、NPM、upstream、TLS 與 Cloudflare。每次只證明一層、只改一項，避免在 DNS、路由器與 Proxy Host 之間來回猜測。

先畫出請求經過的每一層

「網站打不開」不是診斷。先確認請求走哪條路，再找出最後成功的一層與第一個失敗的層。若使用 Cloudflare Tunnel，路徑與傳統 port forwarding 不同，不能混用同一套假設。

層級要證明的事常見證據
1. 用戶端問題是否只發生在單一瀏覽器或網路無痕視窗、另一台裝置、行動網路
2. DNS名稱是否解析到預期公開入口A／AAAA／CNAME 回覆與 resolver
3. 外部入口80／443、NAT 或 Tunnel 是否到得了 NPM逾時、拒絕、Cloudflare 錯誤頁
4. NPM正確 Host 是否啟用且能載入設定Host 狀態、add-on log、HTTP 狀態碼
5. UpstreamNPM 是否能以正確 scheme／IP／port 連到服務直連結果、connection refused／timeout
6. 應用與 TLS應用路徑、WebSocket、憑證鏈是否正確404、101 握手、瀏覽器憑證資訊
排錯期間也不能公開 port 81：管理介面只留在可信任網段。若還沒把 admin@example.com／changeme 立即更換，先完成帳號與密碼更新；不要用「暫時測試」為由把 81 轉送到公網。

建立安全又可比較的證據

  1. 縮小時間窗

    記下發生時間、時區、測試 URL 的改寫代稱、用戶端網路，以及最後一次正常時間。一次只重現一個請求。

  2. 記錄症狀而非機密

    保留 HTTP 狀態碼、錯誤類型與相關的少量 log 行；遮罩網域、公開／私有 IP、Authorization、Cookie、密碼、DNS API token、憑證內容與查詢參數。

  3. 建立對照組

    比較內網直連 upstream、內網經 NPM、外網經公開入口。若使用 Cloudflare，再比較 Tunnel／代理前後，但不要任意切換生產 DNS。

  4. 一次只改一項

    保存前記錄原值。不要同時改 DNS、路由器 port、Forward Scheme 與憑證，否則無法知道是哪一項生效。

完整 log 往往包含主機名稱、IP、URL、User-Agent 或其他可識別資料。提供支援時只貼最少必要片段；若 token、密碼或私鑰已公開，刪文不夠，還要立即輪替。

DNS：先確認名稱走到哪裡

  1. 查詢實際使用的 resolver

    分別從內網與行動網路查 A、AAAA 或 CNAME。記錄結果前遮罩完整網域與 IP。內外結果不同可能是 split DNS，也可能是快取或錯誤記錄。

  2. 比對架構

    傳統 NAT 的 A／AAAA 應導向你的公開入口；Cloudflare proxied 記錄通常回 Cloudflare 位址；Tunnel 的公開 hostname 則由 Cloudflare 路由。不要把看到 Cloudflare IP 誤判成錯誤。

  3. 檢查多餘的 AAAA

    若只有 IPv6 用戶失敗，確認 AAAA 是否真的有可達的 IPv6 入口。不要只修 A 記錄卻忽略用戶端可能優先使用 AAAA。

  4. 等待 TTL 並查權威設定

    本機快取只是其中一層。核對 DNS 供應商目前記錄與 TTL，不要透過反覆刪除／重建製造更多變數。

現象可能原因下一步
NXDOMAIN記錄不存在、名稱拼錯或委派錯誤查權威 DNS 的 zone 與完整名稱
內網正常、外網解析錯split DNS 或公開 zone 設錯分別記錄兩個 resolver 的答案並比對預期架構
部分網路仍到舊 IPTTL／resolver 快取等待 TTL，避免繼續變更
IPv4 正常、部分裝置逾時無效 AAAA 或 IPv6 路徑驗證 IPv6 入口，再決定是否修正 AAAA

80／443：從外部證明入口可達

Woow add-on 宣告 80/tcp 為 HTTP、443/tcp 為 HTTPS、81/tcp 為 Admin。傳統架構通常只把 80／443 導向 HA；Cloudflare Tunnel 架構則不需要路由器對外轉送這些埠。先確認你實際採用哪一種。

  1. 使用真正的外部網路

    關閉手機 Wi-Fi 後測試，避免 NAT loopback 讓內網結果看似外網可達。記錄是 timeout、connection refused、TLS 錯誤還是 HTTP 回應。

  2. 傳統 NAT：核對 80／443

    確認路由器規則的目標是正確 HA 私有 IP，協定為 TCP，且 HA 位址沒有因 DHCP 改變。不要建立 WAN → 81。

  3. 確認沒有 port 衝突或上游阻擋

    若 add-on 無法啟動，查看是否已有其他服務占用 80／81／443。若外部完全 timeout，也要確認 ISP 是否使用 CGNAT 或封鎖入站埠。

  4. Tunnel：不要同時追 NAT

    確認 cloudflared connector 在線、public hostname 指向 NPM 可達的內部 service。Tunnel 失敗時，開更多路由器 port 通常不是修正方式。

HTTP-01 申請憑證需要公開 80 可到達挑戰端點；DNS-01 不要求開放 80。不要因為使用 DNS-01 就假設 443 或 upstream 一定正常，這些是不同層。

Upstream：拆解 502 Bad Gateway

在 NPM 看見 502，通常表示 NPM 已收到請求，但無法從設定的 upstream 取得可用回應。先核對 Forward Scheme、Hostname／IP 與 Port，不要從重申請公開憑證開始。

  1. 從內網直連服務

    以服務實際 scheme 與 port 測試改寫後的 upstream URL。若直連也失敗，先處理應用程式、主機防火牆或服務監聽位址。

  2. 確認不是 localhost 陷阱

    對 add-on 而言，127.0.0.1／localhost 通常指容器自身，不是 HA 主機或另一台設備。使用 NPM 從其網路可達的私有位址或名稱。

  3. 比對 scheme 與 port

    把 HTTP upstream 填成 HTTPS，或把 HTTPS port 當 HTTP 使用，都可能失敗。確認服務是否在該 port 真的說該協定。

  4. 讀同一時間的錯誤

    connection refused 常指該位址／port 沒有服務接受；timed out 常指路由、防火牆或服務無回應。保留錯誤類型，遮罩位址後再分享。

502 線索優先檢查避免的誤動作
connection refusedupstream 服務是否啟動、port 是否正確不要重建 DNS 記錄
timeout路由、防火牆、私有 IP 是否變更不要無限拉長 timeout 掩蓋不可達
wrong version number／握手錯誤Forward Scheme 是否與 upstream TLS 相符不要先更換公開端憑證
只有某一路徑 502／404Custom Location 與應用 base path不要刪掉整個 Proxy Host

SSL：分清申請、套用與用戶端驗證

「SSL 錯誤」至少可能發生在憑證申請、NPM 套用、瀏覽器驗證或 NPM 到 HTTPS upstream 的連線。先看錯誤出現在哪一段。

  1. 確認瀏覽器實際收到的憑證

    檢查 Subject Alternative Name、有效期與簽發鏈是否對應目前網域。只記錄必要欄位，不匯出或分享私鑰。

  2. 確認 Proxy Host 選到正確憑證

    同一張萬用或多網域憑證不代表已自動套到 Host。核對 SSL 分頁選擇、Force SSL 與 Host 狀態。

  3. 申請失敗就檢查 challenge 路徑

    HTTP-01 查 DNS 與外部 80；DNS-01 查 DNS provider、zone 權限與最低權限 token。不要把 token 貼進 log 或問題單。

  4. 排除時間與續期問題

    確認 HA 主機時間正確，並查看接近續期時間的 add-on log。避免因一次失敗重複申請而碰到 CA 速率限制。

不要為了消除警告而關閉用戶端憑證驗證，也不要把 origin 的自簽憑證問題與公開端 Let's Encrypt 憑證混為一談。每一段 TLS 都要單獨確認。

Cloudflare：確認錯誤在哪一側

Cloudflare 官方指出 502／504 表示 Cloudflare 無法與 origin web server 建立聯繫，來源可能是 origin，也可能是 Cloudflare。看到 Cloudflare 頁面不等於 NPM 一定沒收到請求；要用時間、Ray ID 與 origin／Tunnel log 對照。

  1. 辨認是 Proxy 還是 Tunnel

    橘雲 DNS Proxy 通常仍需 Cloudflare 能到公開 origin；Tunnel 則由 cloudflared 主動建立連線。不要用 Tunnel 的修法去加 NAT 規則。

  2. 記錄錯誤碼與 Ray ID

    保留發生時間、Cloudflare 錯誤碼與 Ray ID；送出前仍要遮罩網域與 IP。再查同時段的 NPM 與 cloudflared log。

  3. 在內網驗證 Tunnel service

    確認 cloudflared 設定的 service scheme、私有 IP／hostname 與 port 從 connector 所在網路可達。若它指到錯誤的 HTTPS 或 81，就先修 service。

  4. 不要盲目切 DNS only

    切換會改變公開路徑，可能揭露 origin IP 並影響所有使用者。只有在已核准的維護窗口、了解影響並能回復時才做對照測試。

WebSocket：找出握手或長連線問題

WebSocket 的初始 HTTP Upgrade 成功時通常會看到 101 Switching Protocols。若普通頁面正常、即時更新失敗，才把焦點移到 WebSocket，而不是重做整個 Proxy Host。

  1. 先測 upstream

    確認應用程式的 WS endpoint、scheme 與 path。直連就失敗時，先修應用程式。

  2. 確認 NPM 選項

    編輯 Proxy Host 並啟用 Websockets Support。NPM 2.12.4 官方範本會加入 Upgrade、Connection 與 HTTP/1.1 設定。

  3. 查看握手與關閉碼

    在瀏覽器開發者工具查看 WS 請求：403 偏向授權／來源限制，404 偏向路徑，502 偏向 upstream，成功後斷線則查 timeout 與應用 log。

  4. 逐層比較

    內網經 NPM 正常、經 Cloudflare 失敗時才查該層；兩者都失敗則先留在 NPM／upstream。分享畫面前遮罩 URL、Cookie 與訊息內容。

Logs：只看同一請求的必要片段

Woow add-on 的 patch 把多種 Nginx access／error log 從檔案改導向 /proc/1/fd/1，因此 Home Assistant 的 add-on log 是重要入口；同時 config.yaml 將 */logs 排除在備份外。不要假設一般 Docker 教學中的 /data/logs 適用。

  1. 先重現一個請求

    記下精確時間與預期 Host，避免在大量背景流量中搜尋。

  2. 讀 HA add-on log

    找同一時間附近的 Nginx、NPM backend、certificate 或 reload 訊息。先判斷是啟動、設定語法、upstream 還是 challenge。

  3. 與應用／Tunnel log 對時

    NPM 有請求而 upstream 沒有，問題在兩者之間；cloudflared 有 502 而 NPM 無紀錄，則先查 Tunnel 到 NPM 的 service。

  4. 產生最小化摘錄

    只保留錯誤前後必要行，將真實網域、IP、token、密碼、憑證、Cookie 與完整 URL 改寫。不要上傳整份 log。

狀態碼是方向，不是根因。把它與「哪一層產生」「NPM 是否有同時段紀錄」「upstream 是否收到請求」一起判讀。

常見問題

看到 502，要先重申請 SSL 憑證嗎？
通常不要。先確認 NPM 到 upstream 的 scheme、IP／hostname、port 與可達性。公開端憑證與 upstream 502 是不同層。
用內網 Wi-Fi 測試，能證明 port forwarding 正常嗎？
不能。路由器可能支援 NAT loopback，讓內網測試繞回成功。請用行動網路等真正外部連線測試。
Cloudflare 出錯時可以先切成 DNS only 嗎？
不要盲目切換。這會改變所有使用者的路徑，也可能揭露 origin IP。應先用 Ray ID、時間與 NPM／Tunnel log 定位，經核准後才做可回復測試。
可以把完整 add-on log 貼到 GitHub Issue 嗎？
不可以直接貼。先擷取最小時間窗，遮罩網域、公開／私有 IP、完整 URL、Cookie、Authorization、密碼、DNS token 與憑證資料。
