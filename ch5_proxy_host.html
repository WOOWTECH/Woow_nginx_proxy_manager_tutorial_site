第 5 章

建立第一個 Proxy Host

用一個測試網域把 NPM 收到的 HTTP 要求轉送到既有內部 Web 服務，並從 DNS、NPM 與上游三層逐一驗證。

先看懂要求路徑

Proxy Host 的路徑是「用戶端 → DNS 指向的 NPM 入口 → NPM 依網域比對規則 → 內部 Web 服務」。NPM 不會替你建立 DNS，也不會自動開啟路由器的 NAT；每一層都必須另外正確設定。

app.example.net → NPM 的 80/tcp → http://[內部服務位址]:[服務連接埠]

example.net 與方括號內容都是示意值。真實網域、公私有 IP、密碼、憑證與記錄均屬敏感資料，筆記與求助內容應遮罩。

建立前檢查

項目你要確認的事常見錯誤
上游服務從 NPM 所在網路可連到正確協定與連接埠只確認自己電腦能開，卻忽略 NPM 到上游的路徑
完整網域使用你可控制 DNS 的名稱，例如 app.example.net填入 http://、路徑或連接埠
NPM 入口區域網路測試時，名稱應解析到 NPM 可到達的入口解析到另一台 Web 伺服器
管理安全預設帳密已立即更改，81 僅限可信任管理網路把 81 和 80／443 一起做公網 NAT
回復方案記下原始值，且不修改既有可用 Host直接覆寫正式服務規則

Details 欄位怎麼填

NPM 欄位第一輪建議判斷方式
Domain Namesapp.example.net只填完整網域，不含協定、連接埠與路徑
Scheme依上游實際服務選 http 或 https這是 NPM 到上游的協定，不是訪客端憑證選項
Forward Hostname / IP[內部服務位址]必須是 NPM 本身可解析、可連到的主機；不要把遠端上游誤填成 127.0.0.1
Forward Port[服務連接埠]填上游實際監聽的連接埠，不是固定填 80
Access List先依服務風險決定；Public 代表沒有套用 Access ListPublic 不代表服務天然安全

建立 Proxy Host

  1. 進入 Proxy Hosts

    在 NPM 選擇 Hosts → Proxy Hosts，再按 Add Proxy Host。不要編輯名稱相近的既有規則。

  2. 填入網域

    在 Domain Names 填入測試用完整網域。真實值不要出現在公開截圖或工單。

  3. 設定上游

    依上游實際狀態選 Scheme，填入 NPM 可到達的 Forward Hostname / IP 與 Forward Port。

  4. 選擇基本開關

    一般服務可啟用 Block Common Exploits。只有上游確實使用 WebSocket 時才啟用 Websockets Support；第一輪先不要啟用快取。

  5. 先不處理 SSL

    為了分層排錯，SSL 分頁先選 None，Advanced 保持空白。第 7 章再申請與強制使用憑證。

  6. 儲存並記錄

    按 Save，確認新列為 Enabled。只記下代號、建立時間與設定目的，不抄錄敏感值。

基本開關取捨

Cache Assets 可能改變動態內容的更新表現，初次測試應關閉。Block Common Exploits 是 NPM 提供的額外規則，但不能取代上游更新、驗證與最小暴露。Websockets Support 會處理升級連線；一般網站不必為求「更快」而開啟。

不要直接貼 Advanced 設定：官方介面明確把它留給進階 Nginx 設定。沒有查證上游需求與指令作用前，保持空白。

確認 DNS 命中 NPM

Proxy Host 儲存成功後，名稱仍必須解析到正確入口。傳統對外模式通常是公開 DNS 指向路由器的公開 IP，再由 NAT 把 80／443 送到 NPM；只做區域網路測試時，也可使用你控制的內部 DNS 覆寫。詳細做法在第 6 章。

dig +short A app.example.net
nslookup app.example.net

結果要和你的設計一致，而不是盲目期待某個固定 IP。Cloudflare Proxied 記錄會回覆 Cloudflare IP，不會直接顯示來源站 IP；DNS-only 才會直接回覆記錄目標。

分層測試第一個 Host

  1. 先測上游

    從可代表 NPM 網路位置的裝置開啟上游 URL，確認協定、主機與連接埠確實有回應。不要把含 token 的完整 URL 貼進測試紀錄。

  2. 再查 DNS

    使用 dig 或 nslookup，確認測試裝置得到預期入口。若結果不對，先修 DNS，不要反覆改 Proxy Host。

  3. 測 HTTP 標頭

    執行 curl -I http://app.example.net。狀態碼可能依上游而異；重點是要求有到達預期服務，而非把任何特定狀態碼當作唯一成功標準。

  4. 用瀏覽器驗證功能

    開啟測試網域，檢查登入、靜態資源與即時功能。若應用程式要求 trusted proxies 或外部 URL，僅依該應用程式官方文件調整。

上線前安全檢查

  • NPM 的預設 admin@example.com／changeme 必須已立即更改。
  • 外部 NAT 或防火牆不得開放管理埠 81；傳統模式只把必要的 80／443 導向 NPM。
  • 不要公開本來只應在內網使用的管理後台；需要額外保護時，先規劃 Access List、應用程式驗證或 VPN。
  • SSL 尚未完成前，不要透過公網輸入密碼或其他敏感資料。HTTP 測試僅用無敏感資料的測試頁面。
  • 網域、公私有 IP、密碼、DNS token、憑證與完整 log 都要在分享前遮罩。

Proxy Host 排錯

具體問題可能層級檢查方式
出現 502 Bad GatewayNPM 到上游核對 Scheme、Forward Hostname / IP、Forward Port，並確認上游有監聽且允許 NPM 連入
看到 NPM 預設頁或 404網域比對確認瀏覽器使用的完整網域與 Domain Names 完全一致，且 DNS 指向這台 NPM
連線被拒絕或逾時DNS、入口或 NAT查解析結果、NPM add-on 狀態、80 的防火牆與 NAT；絕對不要改開 81 測試
頁面可開但即時更新失效WebSocket確認上游確實使用 WebSocket，再啟用 Websockets Support 並重新測試
只在外網或只在內網失敗NAT loopback／內外 DNS分別記錄兩邊的 DNS 答案；必要時規劃 hairpin NAT 或 split DNS，不要隨機更換上游位址

常見問題

Domain Names 要填完整 URL 嗎？
不用。填完整網域，例如 app.example.net；不要加入 http://、路徑或連接埠。
Forward Hostname / IP 可以填 localhost 嗎？
只有上游真的和 NPM 在同一執行環境時才可能正確。Woow add-on 中的 127.0.0.1 指向 add-on 自己，不會自動代表 Home Assistant 主機或其他區網裝置。
第一個 Host 一定要啟用 WebSocket 嗎？
不用。只有上游功能需要 WebSocket 時才啟用；它不是通用的效能開關。
為什麼先不申請 SSL？
先把 DNS、NPM 與上游路徑分層驗證，可避免把憑證挑戰錯誤和代理錯誤混在一起。正式輸入敏感資料前仍必須完成 HTTPS。
Public Access List 代表服務可以安全公開嗎？
不代表。它只表示沒有套用 NPM Access List；應用程式本身仍需更新、驗證與適當的安全政策。
